My Quotes, templates (client vs global, the sectioned builder), the flat and sectioned editors, the document, sending, deposits, drafts and the plan tab.

### "My Quotes" (`QuotationsListView`)
- **SECURITY, fixed:** the view had no `get_queryset` at all, so `ListView` fell back to `Quotation.objects.all()` and **every client saw every other client's quotes, lead names and figures**. Scoping is now at the QUERY (never the template), and `_visible_quotations(request)` is the single resolver every per-quote action shares — the old inline `.filter(appointment__tenant=…) if … else Quotation.objects` had to be repeated correctly at four call sites and fell back to EVERY tenant when no workspace resolved. No workspace now means no quotes. **Scoped to the CURRENT WORKSPACE for everybody, the operator included.** The tenant switcher is impersonation ("the dashboard then shows that tenant's world"), so an operator lensed into Barmak must see Barmak's quotes. Letting `is_platform_owner` bypass the lens put Homebase's quote in Barmak's section (prod 2026-09-03) — seeing across clients is now a deliberate `?all=1`, offered only to the operator, re-checked server-side, and shown as a warning strip while it is on. `_viewing_all_tenants` is the single reader; a per-quote action (download, resend, duplicate) never widens past the workspace. The same rule and the same opt-out apply to `QuotationTemplate.for_user`.
- Row: quote number · lead name · created · amount · status · channel sent. `Quotation.sent_channels()` / `sent_channel_label()` read the two independent send flags, so "Email + WhatsApp" and "Not sent" are both real answers. `lead_name()` never returns blank — a nameless lead falls back to the phone number, then the quote number.
- **Every row can edit and delete.** Both actions existed on the quote's own pages and on the appointment's Quotes tab but not on the LIST, so the one screen that shows every quote was the one place you could not change or remove one - a wrong figure meant opening the quote first. `delete_quotation` honours a validated `next` (`safe_return_path`, the same resolver the email send uses): its DEFAULT is the lead's own page, which is right for the appointment's Quotes tab and wrong for the list, where it would throw the plumber onto a lead they were not looking at and lose their page and their search. Delete is a POST form with a confirm, never a link - a GET must not delete - and both actions go through `_visible_quotations` like every other per-quote action, so putting them on the row widened nothing. Pinned by `MyQuotesHistoryTests`.
- **View and Edit are ONE button, "View / Edit", to the editor** (owner request, 2026-09-21), on the quotes list and the lead's Quotes tab. The editor already draws the document the customer gets (the flat live preview, the sectioned sheet itself), so two buttons were two routes to one screen's worth of content. The read-only client copy stays reachable from the editor: "View Quote" on the sectioned sheet, "Client copy" on a flat edit. Pinned by `OneOpenButtonTests`.
- Sorted `-created_at, -id`: `created_at` is `auto_now_add`, so two quotes raised in the same instant would otherwise reorder between page loads. Search covers lead name / quote number / phone; status filter; `paginate_by = 25` with the search preserved across pages; **two distinct empty states** (no quotes yet vs nothing matched). Row actions: view, download PDF (`download_quotation_pdf`, same `build_quotation_pdf_file` the sends use), resend by email or WhatsApp as separate buttons, duplicate.
- **Status is `draft / sent / accepted / cold`** — `rejected` was retired in 0078 with a reversible data migration (0079) so no row is stranded on a value that is no longer in `STATUS_CHOICES`. The vocabulary is shared with the post-visit scheduler on purpose: when that gives up it marks a lead cold, and the quote has to be able to say the same thing.

### Quote templates: client vs global
- **The BUILDER is one template, `bot/pages/quotation_template_form.html`, for create AND edit, and it is the QUOTE EDITOR's layout** — same cards in the same order, the same `.pbq-items-panel` where what is already added stays on screen, the same `.pbq-totals` (its two default-cost inputs carry `pbq-total-input`, the same compact figure box the quote's labour and transport use), and the same `.pbq-actionbar` closing the page on Save. `OneTemplateBuilderTests.QUOTE_SKELETON` measures that parity rather than asserting it: the same blocks, in the same order, on both screens. Building a template is building a quote; a builder that looked like a different product taught a second set of habits for the same job. `create_quotation_template.html` / `edit_quotation_template.html` (835 + 972 lines) are DELETED and a test asserts they stay gone: they had drifted exactly as the three quote editors had — the edit screen printed every figure in RAND ("R 0.00") on a business quoting in US dollars, put Add Item in a card header instead of under the list, and carried a warning block create had never heard of. `TEMPLATE_FORM_TEMPLATE` is the single name and `template_form_context()` the single context builder (`template_mode` = new/edit, `quote_currency` from the lead's own `TenantConfig.currency` — never a symbol typed into the markup).
- The items are still a Django FORMSET (`items-0-description`, …), not the quote editor's JS array; only the markup around those inputs changed, from a nine-column table to one `.pbq-item` card per form. Removing a card ticks the formset's own DELETE box — the row must reach the server marked for deletion, not merely vanish from the DOM — and blank scaffolding cards are dropped the same way on submit, since the formset validates `unit_price` and an untouched spare would fail the save. `extra` dropped 5 → 0 (`min_num=1` renders the one blank card): the quote editor opens on ONE blank item and adds the next when that is filled, and five blanks were cheap as table rows but five screens of scaffolding as cards. **The item card is the quote's card** — description, then qty and unit price side by side, then the line total; `category` and `is_optional` are real fields (the detail page shows them, Duplicate carries them) so they sit in a `<details>` that is SHUT on load rather than being deleted, and a cloned card resets it. What cannot match is what a template does not have: no client or project cards, no lead picker, no document preview, and an action bar of Cancel / Add Item / Save because there is nothing to email, WhatsApp or download.
- **The operator's "share with every client" checkbox is on the EDIT screen too**, and re-checked server-side there as it already was on create. It was create-only, so a template shared by mistake could never be taken back.
- `QuotationTemplate.is_global` (migration 0078). A CLIENT template belongs to its tenant; a GLOBAL one is written by the operator and offered to every tenant read-only, with **Duplicate as the way to make it yours** (`duplicate(new_name, tenant, created_by)` drops an editable copy in the caller's workspace, never another global).
- **`QuotationTemplate.for_user(tenant, user)` and `.editable_by(user, tenant)` are THE single readers** for visibility and permission. A plain `.filter(tenant=…)` hides the global set; a plain `.all()` leaks one tenant's templates. **Visibility is not permission** — a client can SEE a global template and must not edit it, so the two questions are asked separately (`EditQuotationTemplateView.get_object` re-asks after `get_queryset`).
- **SECURITY, fixed:** `duplicate_template`, `delete_template` and `toggle_template_status` fetched by bare pk with no scoping at all, so **any staff user could delete another tenant's template** by guessing a pk. All three now go through `_editable_template`.
- `is_global` on the create form is operator-only AND re-checked server-side in `form_valid` — hiding a checkbox is presentation, not permission. The list's counts are taken over the same set the rows come from (counting by tenant alone excluded every global, so the totals disagreed with the list).

### Quote templates: the builder is the tenant's OWN sheet
- **The builder follows the tenant's quote layout, exactly as the quote editors do.** `builder_template_names(request)` reads the same `is_sectioned` switch `get_template_names()` uses on every quote screen, so a sectioned tenant builds their templates on their own document (`bot/pages/quotation_template_sectioned_form.html`) and a flat tenant keeps `quotation_template_form.html`. Tenant data, never a slug check. Building a template is building a quote, so the builder that looked like a different product taught a second set of habits for the same job — that rule was already why create and edit are one file; this extends it to WHICH sheet.
- The sectioned builder IS the paper quote: the tenant's letterhead (`quote_letterhead.html`), numbered sections each with their own SUB-TOTAL, **QTY | DESCRIPTION | UNIT PRICE | TOTAL PRICE** in the sheet's own order as ONE table, MATERIALS SUB-TOTAL / ADD: Labour / Transport / SUB-TOTAL / VAT / GRAND TOTAL, and the banking + signature foot (`quote_footer.html`). What differs is only what a template does not have: **no client** (the `.bq-meta` grid holds the template's own name, job type and notes in the same shape), **no per-job figures** (VAT, deposit and terms are the business's own Profile defaults, shown where the quote will carry them and greyed — a discount is per job and the paper document has no such row), and **no send** (Cancel / Add Section / Save). Pinned by `SectionedTemplateBuilderTests.SHEET_SKELETON`, which measures the blocks in order rather than asserting the look.
- **Sections are `QuotationTemplateItem.section` + `quantity_text`** (migration 0087), mirroring the same two fields on `QuotationItem`, with `Meta.ordering = ['sort_order', 'id']` — consecutive rows sharing a heading are one section, so the order the lines were typed in IS the grouping. `group_formset_by_section(formset)` groups the FORMS by their **bound** section value, so a rejected save hands back the headings the plumber typed rather than the ones the row was last stored under.
- **It is still the same Django FORMSET** (`items-0-description` …), only the markup around those inputs is the sheet's. The heading is typed once and written onto each row's hidden `section` on input; `quantity_text` is the visible QTY cell and the numeric `quantity` is derived from it (`19 length` → 19); a row added in the browser is stamped out of `{{ formset.empty_form }}` with `__prefix__` replaced, so it posts exactly the fields a server-rendered row does; `sort_order` is re-stamped in DOM order on submit, or a row added to section 1 after section 2 exists would sort into section 2.
- **The flat builder carries `section` and `quantity_text` hidden even though it shows neither** — a global template built on the sectioned sheet can be opened there by the operator, and a field the form did not render comes back blank and wipes the grouping. Editing the NUMBER on that screen clears the wording it no longer matches; editing the price leaves it alone.
- **A template arrives on a quote as its OWN sections.** `useTemplate` in the sectioned editor groups the API's items by heading and calls `addSection` per group; a template with no sections is still one block named after the template, which is what every template used to do. Two long-standing bugs fixed on the way: `?template_id=` was never implemented in `quotation_templates_api`, so the whole list came back and both editors read `[0]` — **the most-used template named the section and supplied the default costs, whichever row was actually tapped** — and the payload never carried `default_labor_cost` / `default_transport_cost` under the names the editors read, so a template's default labour silently arrived as 0 on every quote. `template_items_api` also fetched by **bare pk with no scoping**, handing any staff user another tenant's item list and prices; it goes through `_visible_templates` now, like every other per-template action.
- Known, untouched: the template DETAIL page's "Use Template" button posts to `use_template` with no appointment, and `Quotation.appointment` is non-null, so that button 500s (the working route is `use_template_for_appointment`). The detail page also lists items flat, without their sections.

### Quote screens (mobile-first)
- **The flat quote editor is ONE template, `bot/pages/quote_flat_form.html`, for all three editors** — create-from-lead, standalone (`quotations/new/`) and edit — driven by `quote_mode` (`new` / `create` / `edit`). It is the `/quotations/new/` layout, made the layout everywhere. This mirrors the sectioned side, which was already one template for the same three screens, so both layouts now work identically and `get_template_names()` picks between them PER TENANT (`FLAT_FORM_TEMPLATE` / `SECTIONED_FORM_TEMPLATE`). The three old files (`create_quotation.html`, `standalone_quotation.html`, `edit_quotation.html`, ~2,500 lines) are deleted and a test asserts they stay gone — they had drifted into different headers, two different preview blocks and NO preview on edit, so one quote looked like three products depending on how you reached it. `flat_form_context()` is the one context builder; `QUOTE_PROJECT_TYPES` is the one type list.
- **The DOCUMENT is one include, `bot/includes/quote_flat_document.html`, rendered by both the editor's live preview and the read-only client copy** (styles in `quote_flat_document_css.html`). `quote_live=True` swaps the saved values for the containers the editor's JS writes into; everything else — blocks, order, totals rows — is identical by construction. They had drifted: the view page used a two-column key/value panel and totals of "Labor / Materials / Total" while the editor previewed labelled blocks and "Material / Labour / Transport / Total", so the plumber checked one paper and sent another. **Page chrome stays OUT of the document** — the view page's status/created/sent-via row and its action buttons sit above it in `pbq-no-print` cards, or they would print on the customer's copy. Pinned by `QuoteDocumentParityTests`.
- **`bot/includes/quote_flat_letterhead.html` is the flat document's head, on the editor preview AND the client copy**, so what the plumber checks on screen is what the customer receives. It is fully tenant-driven: the preview hardcoded "HOMEBASE CONSTRUCTION", the strapline, a Johannesburg address and a phone number; the client copy hardcoded "HOMEBASE CONSTRUCTION [PVT] LTD", a Hatfield address, two Homebase numbers and `info@homebaseplumbers.co.zw` (also in its footer) — on EVERY tenant's quote. Absent means omit; the logo falls back to the business name, then its initials, then nothing. `OneQuoteLayoutTests` pins all of it, including that no Homebase value reaches another tenant.
- Six templates make up the quote workflow: `quote_flat_form` (the three flat editors), `view_quotation`, `quotations_list`, and the four template-builder pages. **All of them extend `bot/layouts/base.html` and share one responsive layer, `bot/includes/quote_responsive_css.html` (`pbq-*`)** — include it in `{% block extra_css %}` on any new quote screen rather than re-inventing card/table/modal CSS.
- The mobile contract, pinned by `QuoteMobileLayoutTests` in `bot/test_views_actions.py`: one document per page (view/edit used to emit a whole second `<!DOCTYPE html>` inside the content block, so their `body{background}` painted over the shell); no declared width or `min-width` wider than a phone; the Font Awesome icon set only (`bi bi-*` renders blank — Bootstrap Icons is never loaded); and the shared layer present on every page.
- Wide tables never scroll sideways: read-only ones take `.pbq-table--stack` and editable ones `.pbq-table--edit`, and **every `<td>` must carry a `data-label`** — below 768px the header row is hidden and each cell prints its own label as the row becomes a card. `.pbq-table--edit` uses `!important` on `display`/`width` deliberately: it sits over legacy page CSS that pins column widths with `nth-child`, which would otherwise outrank it. Key/value panels use `.pbq-kv` (a list, identical at 320px and 1440px) instead of a one-column table.
- **The action bar (`.pbq-actionbar`) closes the page and is NEVER pinned to the viewport** (owner rule, 2026-09-08): 4-up in flow at the very bottom, 2x2 below 768px, reached once the sheet is filled in. It used to be `position: sticky` offset by `--bottom-nav-h`, which sat over the form on a short screen and made every quote screen read as a floating toolbar; the `.pbq-page--barred` modifier existed only to clear it and is retired with it, as is the sectioned sheet's own `.bq-actions--bottom` stickiness. **Nothing in the quote layer pins to the viewport** — if a future bar needs to, note that `.pb-content__inner` runs `pb-fadein` with `animation-fill-mode: both`, and a retained `transform` would make it the containing block for fixed descendants (which is why that keyframe ends on `transform: none`; **don't put a `translateY(0)` back**).
- `quotations_list` is `paginate_by = 25` and now renders page controls; without them everything past the first 25 quotes was unreachable.
- **The item editors keep what is already on the quote on screen while the next item is typed.** All five (`create_quotation`, `standalone_quotation`, `edit_quotation`, and both template builders) wrap their list in `.pbq-items-panel`: a running count/subtotal bar (`#itemsCount` / `#itemsRunningTotal`, refreshed from the single `calculateTotals`/`calculateAllTotals` → `updateItemsBar` choke point so it can't drift), the list itself (`#itemsScroll`), then Add Item. Past `ITEMS_CAP_AT` rows JS adds `.is-capped`, which gives the list its own scrollbar — Add Item is deliberately **not** viewport-sticky, since a second sticky element lands behind `.pbq-actionbar` on a phone. Revealing a new row uses `block: 'nearest'` (or a scroll of the list's own box to its bottom); `block: 'center'` pushed every item already added out of the viewport, which with the keyboard up left the blank new row as the only thing on screen. `renderItems` restores `scrollTop` across its innerHTML rebuild.
- The template builders' totals were moved **out of the table's `<tfoot>`** into a `.pbq-totals` block below the list — inside the table they would scroll away with the rows once the list is capped. Their `addNewRow(reveal)` only scrolls/focuses when `reveal` is true: `checkIfNewRowNeeded` auto-appends a row as you type a price, and focusing there would yank the caret out of the field being filled.
- **Watch the temporal dead zone in these handlers.** `create_quotation_template` calls `calculateAllTotals()` at the top of its `DOMContentLoaded`, and that reads `ITEMS_CAP_AT`; declaring the `const` further down threw a `ReferenceError` that killed the whole handler — no totals, no delete buttons, no auto-add — on a page still returning 200. Static checks can't see this; run the rendered page in jsdom.
- **Line-item ids come from a monotonic `nextItemId()`, never `Date.now()`.** Every lookup is by id, and two items added inside the same millisecond shared one — editing one edited both, removing one removed both.

### The sectioned quote document (per tenant)
- A tenant whose `TenantProfile.letterhead['layout'] == 'sectioned'` gets their **own quote sheet** instead of the flat one: letterhead, numbered sections each with their own SUB-TOTAL, then labour / transport / discount / VAT / GRAND TOTAL, terms, banking details and a signature line. Barmak Plumbing is the first (seeded by migration 0070, scoped to slug `barmak-plumbing`, no-op elsewhere, fills blanks only). **The switch is tenant data, never a slug check in code** — that is what makes "for Barmak only" hold: `TenantConfig.quote_layout()` / `.letterhead()` read the lead's OWN tenant, and `quote_layout.tenant_of()` prefers the lead's tenant over the request's so a staff member with several memberships still gets the right sheet.
- All four screens switch together via `get_template_names()`: create-from-lead, standalone new quote, edit and view (`bot/pages/quote_sectioned_form.html` for the three editors — one template, since the sheet carries its own client fields — and `quote_sectioned_view.html` for the client copy). Styles/letterhead/footer live in `bot/includes/quote_sectioned_css.html`, `quote_letterhead.html`, `quote_footer.html`.
- **Every letterhead value is optional and absent means omit** — a tenant with no bank details gets no Banking Details block, never another tenant's. Edited on the Profile page (`letterhead_submit` form → `_save_letterhead` in `auth_views.py`); the address writes through to `location_line`.
- Storage: `QuotationItem.section` groups the lines (consecutive same-title items form one section, so insertion order matters — hence `QuotationItem.Meta.ordering = ['id']`), `QuotationItem.quantity_text` keeps the trade wording ("19 length") while `quantity` keeps the number the line total uses, and `Quotation.discount` / `vat_percent` carry the rest. **Payment terms are the quotation's `notes`, one per line** — a sectioned quote has no notes box. `Quotation.save()` now takes discount off the gross and adds VAT to the remainder; both default to 0, so every pre-existing quote totals exactly as before.
- The sectioned sheet posts `materials_cost: 0` on purpose: its materials are the item lines, and `save()` adds `items_total + materials_cost`, so sending both would double-count. **Note the flat layout still does send both** — `create_quotation_api` stores a `total_amount` higher than the figure the page showed. Pre-existing, deliberately not changed here.

### The fix-and-supply sheet (Homebase's own layout)
- **`letterhead.layout = "fix_and_supply"` is Homebase's standard quote layout for everything in its quotation system** (owner request, 2026-09-26, from Homebase's paper quote "Tinaye bathroom renovation"): the editor, the client copy, the template builder and the PDF. Seeded by migration 0099 (slug `homebase`, fills blanks only, same pattern as Barmak's 0070). The switch is tenant data, never a slug check; the Profile page's layout select (`lh_layout`: standard / sectioned / fix_and_supply) replaces the old tickbox, and a lone legacy `lh_sectioned` post is still read.
- The paper, block for block: logo | company name | contacts (with the paper's own "Cell;", "Email;", "Website;" labels), "Quotation" centred and underlined, Client Name with the date (dd/mm/yyyy) on the right, ONE grey-ruled, striped table led by **DESCRIPTION | QTY | UNIT | TOTAL** with no header row, item groups split by a blank row, then Material cost / Labour / Transport cost / **Total fix and supply**, yellow-highlighted with blank rows between them, then **Bank Details | Fix and Supply | Total | figure** (the figure white on black), the tagline in quotes at the foot and a faint diagonal watermark. There is no signature line, no numbered section titles and no per-section subtotal, because the paper has none.
- **It rides the sectioned machinery rather than getting its own editor.** `quote_layout.SHEET_LAYOUTS` holds both sheets and `is_sectioned()` is true for both, so the grouped editor / view / builder / PDF entry points serve it; the look branches on `lh.layout` (now carried in `TenantConfig.letterhead()`). The overlay is `quote_fs_css.html` (loaded after the sectioned CSS, only for this layout), `quote_fs_letterhead.html` and `quote_fs_foot.html` (reached through `quote_letterhead.html` / `quote_footer.html`), and `quote_fs_script.html`, which moves DESCRIPTION before QTY in every row and `<colgroup>` however the row was built, and mirrors `#t-grand` into the black total box. A second 1,000-line editor would have drifted from the first as the three flat editors once did. The PDF is `_fix_supply_sheet` in `quote_pdf.py`, checked BEFORE `is_sectioned`; its letterhead, watermark and tagline repeat on every page through `_Sheet.on_new_page`.
- **Group titles never print, and a blank one is stored as "GROUP n"** (editor `collect()`, builder `syncSection`): two blank-titled groups in a row would otherwise reopen as ONE group (`group_items` joins consecutive rows sharing a title) and lose the blank row between the plumbing and the tiling.
- Discount and VAT rows are hidden while zero (`.bq-fs-off`) and show when the quote carries a figure; their inputs stay in the form, so a saved figure is never dropped. The deposit row follows the usual rule (only when set). Contact / address / email sit in a `bq-no-print` strip on the editor: the paper prints only the client name, but the sends need them.
- **The sheet's address is `letterhead.sheet_address`, not `location_line`.** `location_line` is also what the assistant SAYS ("We're in Hatfield, Harare." on Homebase), which is not a letterhead address and cannot be edited into one without changing WhatsApp copy. `address_lines` splits the sheet address on commas. `company_name` (the registered name heading the sheet) and `watermark` are optional letterhead keys too; absent means the business name and no watermark.
- **The sheet's inputs repeat the dashboard's own input selector** (`.pb-content input:not(...)` x3) under `.bq-sheet--fs`. That dashboard rule turns every input into a tall pale-blue pill and outranked the sheet's rules, so a blank `/quotations/new/` read as a web form rather than the paper. Keep the repeated selector when editing `quote_fs_css.html`, or the pills come back.
- Pinned by `FixAndSupplySheetTests` (every screen including `/quotations/new/` draws it, the client copy reads like the paper, nothing crosses to a sectioned or flat tenant, the PDF, the Profile select, the seed migration).

### The editor's own workflow: find the lead, start from a template, save, send
- **The screen is ordered the way the job is done**, on BOTH layouts: who the quote is for and where its lines come from at the TOP, the sheet in the middle, and everything that DOES something in one bar at the BOTTOM. The sectioned sheet had Save alone above a sheet nobody had filled in yet, no template loader, no lead picker and NO send buttons at all — the plumber saved, navigated to the quote page, and sent from a screen they had already left.
- **`bot/includes/quote_lead_picker.html` is the one lead picker**, on both editors and only where a lead can still be attached (never on an edit, which already has one). It renders the search box and calls `window.quoteLeadPicked(lead)`; each editor defines that and fills its own fields, so the include knows how to FIND a lead and never what a sheet does with one. `appointment_search_api` had existed for exactly this and no screen used it: the only route to a quote for a lead was to find them in the inbox and open them first. **An EMPTY query now answers with the 8 most recent leads** — "who have I been talking to?" is the real question, and returning nothing until two characters were typed made attaching a lead a memory test. It also matches on email, and never offers `quotation_only_` / `email_` stubs.
- **Three includes are shared by both layouts** rather than copied into each: `quote_template_modal.html`, `quote_email_choice_modal.html` and the picker. Their CSS lives in `quote_responsive_css.html` (the `.pbq-choice*` rules moved there from the flat page): **a `<style>` block rendered AFTER the document moves the "past the stylesheets" line every parity test measures from**, so shared chrome keeps its styles in the shared layer, never in the include.
- **Every send saves first, on both layouts** (`persist()` → send). Save and the two channels are independent and never disabled; the channels stay separate as they are everywhere else.
- **Save, Email and WhatsApp all hand the plumber back to the page the editor was opened from** (`quote_return_url` → the editors' `RETURN_URL` / `returnToCaller`). Raising a quote is a detour out of a lead's screen, the quotes list or the diary, and the three buttons that finish the job used to end in three different places: a brand-new Save landed on the quote's own view page, an edit's Save left the plumber standing on the editor with only a toast, and a send left them on the sheet with no way of telling whether it had gone. The target is resolved SERVER-SIDE from the Referer at render time, so the plan tab and the lead picker cannot move it, and only the PATH is emitted so it can never be an open redirect; a Referer pointing at an editor (a reload, a hop between the two sheets) is rejected and falls back to the lead's own page, then to the quotes list for a standalone quote whose lead is a synthetic stub. **Two things must not be navigated over:** a WhatsApp handoff whose popup was BLOCKED is running in this tab (return only when `opened` exists), and the manual `mailto:` route is pulling the PDF down through a hidden iframe on this page (hence the longer delay, and `markSent` is awaited now that the page leaves). A FAILED send keeps them on the sheet, which is what needs fixing. Pinned by `QuoteReturnToCallerTests`.
- **A quote is sendable on at least one channel, always.** `Quotation.client_phone` (migration 0086) keeps the number typed on the sheet, because a standalone quote's lead is a stub whose `phone_number` is a synthetic key — that key is what keeps these rows out of every proactive send, so it must NOT be replaced with a real number. `quote_send_digits(quotation, appointment)` is the single resolver (lead's own number, else the typed one, digits only) and both the handoff and `flat_form_context` read it. A missing EMAIL is a missing detail, not a closed door: the quotes list, both client copies and both editors point at the screen where the address is added instead of showing a disabled button, and WhatsApp is never gated behind it.
- **The deposit is a figure on the quote, adjustable per job** (`Quotation.deposit_percent`, migration 0086). It only ever existed as words in the payment terms ("deposit 75%"), which could be printed but never changed for a job agreed differently. Asked for as a PERCENTAGE with `Quotation.deposit_amount()` derived from the grand total — a stored amount would stop agreeing with a total that moves on every edit. **The quote's own field is the ONE place it is set, and a new quote opens at 0** (owner rule, 2026-09-21): the plumber types what was agreed for that job. It used to start from the tenant's own `letterhead['default_deposit_percent']`, edited on the Profile page, which made the same figure adjustable in two places and opened every sheet asking for a percentage nobody had agreed. That key is gone from `TenantConfig.letterhead()` (absent from the schema on purpose, so no screen can read it back in), from the Profile form, and from the sectioned TEMPLATE builder's preview - and `_save_letterhead` POPS a figure written before the rule, so an old letterhead cannot seed one. It is clamped 0-100 in the editor AND in `_deposit_percent()` on the way in, and **0% means the row is absent from every document** — screen, client copy and PDF, both layouts. Absent from a payload means UNCHANGED on an edit, so a caller that never heard of deposits cannot clear one. Pinned by `QuoteDepositTests`.
- **A new quote's payment terms never carry a deposit line** (`quote_layout.default_terms`, owner rule, 2026-09-21). The tenant's default terms seed a new quote, a template preview and a saved quote with no terms of its own, and any line naming the deposit (English, plus the Shona loanword) is filtered out at that seeding: a "deposit 75%" boilerplate line printed a figure nobody set for THIS job, and contradicted the deposit row whenever the two differed. The Profile keeps what the tenant typed (and says it is not carried); a deposit line the plumber types on one quote is theirs and is kept. Pinned by `QuoteDepositTests` and `SectionedQuoteTests`.
- Two long-standing breakages fixed on the way: `create_standalone_quotation_api` did `from .models import …` inside `bot/views/`, so **every save of a quote with no lead 500'd** — the "New Quote" screen could not save at all; and `_sectioned_form_context` took only the quotation, so the sectioned EDIT screen rendered CLIENT / CONTACT / ADDRESS / EMAIL empty and then refused the save ("enter the client name" about a name it had forgotten to draw). The standalone endpoint now also stores sections, trade quantities, discount, VAT, deposit and terms, so a sectioned quote raised without a lead reopens as the sheet it was; `duplicate_quotation` carries the same set.
- **The quote screen has two tabs stuck to the top: QUOTE and PLAN** (`bot/includes/quote_plan_tabs.html`, one include for both layouts). A quote is typed off a drawing, and the drawing was on the LEAD's page: the loop was leave the quote, find the plan block, open the plan, read one number, come back, find your place in the item list, twenty times a quote, on a phone, on site. **Switching tabs does not navigate** — the quote panel (`#pbqQuotePanel`, which is the whole existing sheet, wrapped) is HIDDEN, never unloaded, so every field, the item list, its own scrollbar and the CARET come back exactly as they were; `show()` saves and restores `.pb-content`'s `scrollTop` (the page itself never scrolls — the shell is `height:100vh; overflow:hidden`, so `window.scrollY` is always 0 here) plus `#itemsScroll` and the focused field's selection range, and blurs on the way out so the plan gets the whole screen. The draft autosave is the safety net under this, not the mechanism. Behind the second tab: the customer's **own words verbatim** (`project_description`, `white-space: pre-wrap` — they typed it as a WhatsApp message and the line breaks are part of what they said) then every file they sent. **`quote_lead_panel(lead)` is the one resolver**, called by BOTH `flat_form_context` and `_sectioned_form_context`, and files are addressed by INDEX into `get_all_uploaded_files()` and streamed through `serve_document` — never a storage URL, since R2's presigned links expire and a mis-set backend hands back a bare path that 404s (same reason the lead page links them that way). **Media loads on FIRST OPEN** (`data-pbq-src` -> `src`), because a plan is often several MB and this screen is used on mobile data. Any quote with a lead gets the tab bar, even a lead with nothing on file: behind the tab is Add plan (`#pbqPlanAdd`), which uploads by fetch to `_attach_plan` and rebuilds the file list from its answer, so the plumber never leaves the sheet. Only a brand-new standalone sheet, with no lead to put a plan on, gets no tabs. The full-screen link is `target=_blank` on purpose — an iPhone renders only the first page of an embedded PDF, and leaving the page is exactly what the draft covers. The include's script wires on **DOMContentLoaded, not at parse time**: it sits ABOVE the panel it switches to, and looking `#pbqQuotePanel` up inline left both tabs inert. Printing from the plan tab still prints the quote (`beforeprint` switches back, and the print stylesheet un-hides `#pbqQuotePanel[hidden]`). **This bar is the ONE deliberate exception to "nothing in the quote layer pins to the viewport"** (owner rule, 2026-09-08): that rule was written about a permanent ACTION bar sitting over a form nobody had filled in yet, while this is the only way back from the plan and has to be reachable from wherever the plumber has scrolled. Pinned by `QuotePlanTabTests`.
- **A quote in progress survives Back, a closed tab and a dead battery.** Both editors keep the sheet in `localStorage` as it is typed (debounced 400ms) and flush it on `pagehide` / `visibilitychange:hidden` / `beforeunload` — the events that survive a tab close or a phone switching apps, where `unload` does not — so the keystroke still sitting in the debounce is not the one that is lost. On the next visit to that editor the saved record loads FIRST and the draft is laid on top, because the draft is the more recent thing the plumber typed. **The key follows the QUOTE, not the screen** (`draftKey()` / `bqDraftKey()`): once a save returns a row id the draft belongs to that row, so the same work is found again from the edit screen AND a fresh create screen for the same lead opens blank rather than restoring a quote already raised. A save clears every key the page could hold one under (`draftKeysSeen`), not just the one this page load wrote — the copy that reopens the screen is whichever is still on disk, and the key it was written under may belong to a PREVIOUS page load (that is the bug the jsdom run caught: `new_new` survived the save and came back on the next new quote). Only the sheet's own inputs mark it dirty (`isDraftField` / `bqIsDraftField`): the lead picker's search box and the template modal's live on these pages too, and a draft written from them greets the next visit with "restored your unsaved changes" over a sheet nobody touched. Best effort throughout — every storage call is wrapped, so a browser with site data blocked simply behaves as before. **The quote TEMPLATE builder has none of this**: it is a Django formset, not the editors' JS array.
