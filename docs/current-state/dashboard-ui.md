The sidebar, the detail page (date/time form, compact header, chat composer), the diary, lead search, the inbox date window, and mobile parity.

### The sidebar (`bot/templates/bot/includes/main_nav.html`, `mobile_nav.html`)
- **The money screens are ONE item.** My Quotes, New Quotation, Templates and My Offer are one job - raising and pricing work - and sat as four of eleven top-level entries. They are now a `<details>`/`<summary>` group, "Quotes & Pricing": no JS, keyboard-accessible, and rendered `open` on its own pages, because a nav that hides the page you are reading is worse than a long nav. The parent is tinted by `:has(.active)` and never takes the child's `active` treatment - two items claiming to be the current page is the bug that produces. The mobile sheet uses a `pb-sheet__label` section instead of a second accordion: an accordion inside a bottom sheet is two taps to reach one page.
- **`context_processors.QUOTES_NAV_GROUP` is the single answer to "is this page in the group?"**, read by the desktop accordion and the mobile More button, and resolved off `NAV_MAP` - so a quote page missing from NAV_MAP renders with the group shut over itself. That is what rotted before: `view_quotation`, `create_quotation`, `edit_quotation` and `quotations_list` were absent, so working on a quote left the whole sidebar showing nothing selected, and `gallery` + the quotes group never lit the mobile More button. Any new quote screen gets a NAV_MAP entry and a case in `QuotesNavGroupTests`.
- **ONE nav bar on screen, always: `chromeless` is the flag and `context_processors.in_app_frame` the single reader.** The conversations workspace and the follow-ups dashboard load a whole page into a pane and mark it `frame=1`; the quote editors extend the full layout and nothing told them where they were, so "New Quote" or "Edit" pressed on a lead's Quotes tab rendered a SECOND sidebar and bottom bar inside the frame, under the ones already on screen. `base.html` now renders neither nav when `chromeless`, and `.pb-shell--chromeless` drops the bottom-bar clearance with them. The page is otherwise untouched - it keeps `.pb-content` as its scroller, which is why this is NOT the panel layout (`base_template`, the older answer for the appointment detail and the job screens, swaps the layout outright for pages that also need the panel's fixed height; both stay). `AppointmentDetailView` passes `frame_query` (`?frame=1` in a frame, else empty) and every link leaving that page for a whole page of its own carries it; `quote_return_url` keeps it on the fallback, so a Save hands back INTO the frame rather than landing the pane on a chromed lead page. The Quotes tab's "Add email" link dropped its `target="_top"` with this - taking over the whole window was only ever a way round the second nav. **Any new link out of a framed screen to a full page carries `frame_query`.** Pinned by `OneNavBarInsideTheFrameTests`.
- **The frame context travels WHOLE, and three layers carry it.** `frame` alone got the nav right and then, on the way back to the lead, drew the lead page's own TAB bar in the conversations pane, because that pane also loads with `hidetabs=1&source=conversations`. `context_processors.FRAME_CONTEXT_KEYS` (`frame`, `hidetabs`, `source`) is the set, `frame_params` / `with_frame` the readers. (1) Server-rendered links: `frame_query`, now built ONCE in the `plumbot_shell` context processor (the detail view's own copy is gone). (2) Redirects: `bot.middleware.FrameContextMiddleware` adds the context to any LOCAL redirect answered to a framed request, so a `reverse()`-built landing (delete a quote from its framed page -> the lead page) no longer comes back chromed; off-site and protocol-relative Locations are never touched, and a key the Location already names keeps its own value. (3) Everything else: `bot/includes/frame_links.html`, on `base.html` when chromeless and always on `panel.html`, adds the context on click/submit to same-origin links and form actions that do not already say `frame`, leaving `target="_top"`/`_blank`, anchors and mailto/tel alone. The script is the net, not the mechanism: known links still carry `frame_query` so a test can see them. The viewing path was the one still leaking (the framed Quotes tab's View link and the WhatsApp handoff opened chromed pages). Pinned by `OneNavBarInsideTheFrameTests`.
- **A plan can be added from the portal** (`AppointmentDetailView._attach_plan`). It used to reach a lead only by WhatsApp: the Details tab drew its plan block only once a plan existed or was expected, with Replace as the only control, so a plan handed over on site or by email had no way in. The block is now ALWAYS drawn, with Add plan when nothing is on file; the quote editor's Plan tab posts to the same handler. PDF or image only, checked server-side on extension AND declared type (the input's `accept` is a hint, not a guard). An `X-Requested-With` post gets JSON carrying the WHOLE refreshed file list, because a first plan becomes index 0 and shifts every other file's index; the plain form keeps its redirect. Scoped by the view's own queryset, so another tenant's lead 404s. Pinned by `PortalPlanUploadTests`.

### The detail form's date and time
- **`Appointment.active_slot_field()` is the single resolver for WHICH datetime a row's appointment lives in**, and `_reschedule_slot` delegates to it. One row can hold two - `schedule_job_appointment` flips `appointment_type` and fills `job_scheduled_datetime`, leaving the finished site visit in `scheduled_datetime` - so the bot's reschedule flow and the dashboard's own edit form must not answer this question differently.
- **The Edit Details form has ONE date-and-time box and it edits that slot.** `AppointmentDetailView.post` used to branch on the type and then read a `job_scheduled_datetime` POST key **this form has never rendered**, so on a job row the date and time the plumber typed came from a key that was not in the POST and was dropped silently, under "Appointment updated successfully!". The other half of the same branch called `strptime(..., "%Y-%m-%d %H:%M")` on a value a `datetime-local` input never produces (it sends a `T`). The label and value come from the VIEW (`slot_label` / `slot_datetime`) and are never re-derived in the markup: a job row that rendered its finished visit's date into that box would write it over the job's own datetime on save.
- **Blank means CLEAR; a missing key means "not on this form".** `_parse_local_datetime` returns None for an empty value, and the handler checks `'<field>' in request.POST`. The old `if raw:` could not tell an emptied box from an untouched one, so a date could be set from this form but never taken off. The distinction matters because the plan-upload form and the site-visit banner's forms post to this same view.
- **A moved visit gets a fresh `end_datetime`.** `Appointment.save()` fills it only while it is empty, so a move otherwise keeps the end of the slot the row used to hold; a move to an EARLIER time is the one that bites, since the stale end is still later than the new start and so passes every staleness guard (`post_visit.visit_end`). Pinned in `AppointmentLifecycleActionTests`.

### The dashboard's diary (`_dashboard_workspace_data`)
- One helper feeds the Dashboard page AND the appointment-detail "dashboard" source sidebar. **A job is the lead's OWN row** — `appointment_type='job_appointment'` + `job_scheduled_datetime` (see `Appointment.schedule_job_appointment`, one row, not two) — which is what the jobs board, `send_job_reminders` and `_reschedule_slot` all read. The `bot.models.Job` table is written by nothing in the app (only a test); the dashboard used to read it, so "Jobs This Week" showed 0 however many were booked, and that query was unscoped besides. Never query `Job.objects` for a real figure.
- **The schedule is never filtered by `last_customer_response`.** It is date-scoped already (today / tomorrow / rest of the week); the old `response_age` window on top could only ever hide a real booking whose customer had gone quiet — a visit booked more than 7 days out simply disappeared. The inert window pills came off the detail sidebar with it.
- A booking is `status='confirmed'` on every surface, the week list included (it used to also admit `pending`, so a proposed slot appeared there and nowhere else). `week_appointment_count` is the WHOLE week from today — the metric card's "This week" figure, which previously counted only the days after tomorrow and so read "Today's Appts 1 / This week: 0". Pinned by `DashboardScheduleTests`.

### Finding a lead (`bot/lead_search.py`)
- **ONE resolver for "find me this lead", read by three screens**: the conversations inbox, the priority-leads board and the quote editors' lead picker (`appointment_search_api`). `filter_leads(queryset, query)` searches name / phone / area / email / project type; three separate searches would each have their own idea of which fields count, and a lead that turns up on one page and not another reads as missing data rather than as a filter.
- **A phone number is matched on its DIGITS**, with a local leading 0 dropped (`phone_digits`): people type "077 123 4567" or "+263 77 123 4567" while the row stores `whatsapp:+263771234567`, and matching the string as typed found nothing — which reads as "we have no such lead".
- **A SEARCH IGNORES THE DATE WINDOW**, on both the inbox (`_age_cutoff`) and the board (`_priority_leads_workspace_data`'s time horizon), and both say so on screen while it is on. You search to go and find one particular person, and that person is usually the one who has gone quiet, which is exactly what those windows filter out; searching inside them answered "no such lead" about a lead we hold. The inbox's tab COUNTS follow the same rule as its rows, or the tabs describe a different set from the list.
- The inbox's search used to be a JS filter over the 20 rows already rendered — it could not reach page 2 or anything outside the window, and it was `display:none` below 640px, which hid the only way to find a lead on the device the plumber carries. It is a GET form now (`q`), carried across the tabs, the date select and the pager, with its own empty state ("no lead matches X" is not "you have no conversations"). The priority board had no search at all. Pinned by `LeadSearchTests`.

### The lead inbox's date window (`ConversationsView`)
- **Every tab defaults to `since_wed`** — leads whose `last_customer_response` landed since local midnight on the most recent Wednesday, the day the business's week turns. `_last_wednesday()` takes the most recent Wednesday BEFORE today, so on a Wednesday it reaches back a full week rather than to this morning: a default window that collapsed to a few hours one day in seven would read as an empty inbox rather than as a filter. The fixed-length options (7 / 21 / 30 days, all time) still widen it.
- `_age_cutoff()` is the ONE place a window becomes a moment, read by both the row queryset and the `base_qs` behind the tab counts, so the figures and the list can never describe different spans. The Booked tab still measures `booked_at` (a conversion is dated by its booking), every other tab the lead's last response. Pinned by `ConversationDateWindowTests`.

### Convention: The detail header is compact below 640px
- **The detail header is compact below 640px** (owner request, 2026-09-14). Header + three WRAPPED rows of status pills + the tab bar came to roughly 400px of a ~740px phone screen. The pills are now ONE swipeable strip (`flex-wrap: nowrap; overflow-x: auto`, scrollbar hidden, children `flex: 0 0 auto`) rather than three stacked rows, which is where most of the height was; **no pill is dropped** - shrinking is the brief, hiding a status the plumber reads is not, so a `display:none` in `.appt-pill` fails a test. The one thing removed is the `Score n/100` sentence sitting immediately right of a chip that already reads `n` (`.appt-score-text`, which also stopped being an inline style so the mobile layer can reach it). Avatar 42->32, tighter paddings, and `.appt-tab-btn` keeps `min-height: 44px` so tightening the chrome never shrinks a tap target. Also fixed on the way: `.appt-detail-meta` printed `appointment.phone_number` RAW, so the stored `whatsapp:+263...` key truncated to "whatsa..." under a name that had already `|cut:"whatsapp:"` - a line of pure noise. Pinned by `CompactDetailHeaderTests`. **Note the page has FOUR separate `@media (max-width: 640px)` blocks**, so a test asking "is this rule in the mobile layer?" must brace-match and concatenate all of them (`_media` does); taking the first answers no for rules that are plainly there.

### Convention: The Chat tab's composer folds on a phone; the transcript is what the tab is for
- **The Chat tab's composer folds on a phone; the transcript is what the tab is for** (owner report, 2026-09-14). Stacked below 768px the composer runs to about 500px - five action pills, then a PDF form that becomes three full-width rows, then the message box - and `.appt-chat-scroll` is the `flex: 1` child, so it is what gives way: the tab showed a screenful of controls and a sliver of conversation. `.appt-quick-actions` and the PDF form now sit in `.appt-compose-extras` behind `.appt-compose-toggle`, which is `display:none` on desktop (no fold there, and no control that would do nothing). **The message box and Send are never inside the fold** - typing a reply is the one thing the tab exists for. A backstop under it caps `.appt-chat-compose` at `max-height: 55%` with its own `overflow-y`, so whatever the extras grow into they scroll inside themselves instead of pushing the transcript out. Both `min-height: 0` declarations (`.appt-chat-pane`, `.appt-chat-scroll`) are load-bearing: without them the flex children refuse to shrink and the pane overflows instead. Note this surfaced only once `.pb-shell` moved to `100dvh` - under `100vh` the shell was taller than the visible area by the height of the URL bar, and the transcript was living on that overhang. Pinned by `ChatComposerTests`.

### Convention: A phone can do everything a desk can, and zoom never costs anything
- **A phone can do everything a desk can, and zoom never costs anything** (owner rule, 2026-09-14). The sidebar is `display:none` below 768px, so **every destination in `main_nav.html` must have a counterpart in `mobile_nav.html`** - the bottom bar or its More sheet. Two did not: `platform_console` and the `switch_tenant` workspace picker were desktop-only, so an operator on a phone was locked into whichever tenant they last chose at a desk with no way into the console. Both gates (`user.is_superuser`, `platform_tenants|length > 1`) are mirrored exactly, never widened. **Zoom rules:** no viewport may carry `maximum-scale` or `user-scalable=no` (the three staff layouts capped it at 5x; capping it is the browser's call); form controls are **16px at <=767px as a CSS rule in `plumbot_variables_css.html`**, never a JS pass - iOS zooms the page in on a focused field under 16px and does not zoom back out, and the JS this replaced ran once at DOMContentLoaded, so it stamped an inline size on the fields that existed and missed every quote item row the plumber added afterwards (an inline style also outranks the mobile layer, so a JS pass overrides that rule rather than reinforcing it). `.pb-shell` takes `height:100dvh` with the `100vh` line kept above it as the fallback - `100vh` on a phone is the viewport with the URL bar HIDDEN, and the shell does not scroll, so while the bar shows that surplus is unreachable. `.pb-bottomnav` and `.pb-content`'s clearance both add `env(safe-area-inset-bottom)`, or the bar's lowest row of taps lands in the gesture area. **Wide tables scroll inside their own box** (`.pb-table-scroll`, the global counterpart of the quote layer's `.pbq-table--stack`), never the page's, which would drag the header and every other card sideways with it; a table that constrains itself (`table-layout:fixed` + `overflow-wrap`, as the sectioned quote sheet does) needs no wrapper. Prefer `getComputedStyle(el).display` over `window.innerWidth` when JS needs to know the layout state, so it cannot disagree with the media queries under zoom (`followup_dashboard` does this to fall back from its iframe pane to plain navigation). Pinned by `MobileParityTests`, `MobileZoomTests` and `WideTableTests` in `bot/test_template_audit.py` - the parity case renders the sheet for a real superuser, since a static tag check would pass while a missing context variable kept the control invisible.
