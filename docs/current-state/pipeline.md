Inbound pipeline, unified classifier, conversation storage, quoted replies, the reasoning controller, and the outbound chain every reply goes through.

### Stack & composition
- Django app `bot/` on Railway; WhatsApp via Twilio/Meta Cloud API; all AI via **DeepSeek** through the OpenAI SDK pointed at `api.deepseek.com`.
- The shared DeepSeek client (`bot/services/clients.py`) monkey-patches `chat.completions.create` to **force "thinking" mode off on every call** — thinking mode ate the `max_tokens` budget and returned empty/truncated JSON, breaking every classifier (`DEEPSEEK_THINKING=enabled` reverts).
- `Plumbot` (`bot/views/plumbot/`) is one class composed from mixins — `state`, `response`, `extraction`, `availability`, `booking`, `reschedule`, `notification`, `plan_upload`; `base.py` wires them and `get_or_create`s the `Appointment` per phone number.

### Inbound pipeline (`bot/whatsapp_webhook.py`)
- `process_message_change` → `handle_text_message(sender, text, message_id, quoted_id)` logs the user turn, resolves any quoted reply, then **debounce-batches per sender** (`_enqueue_for_response` / `_flush_text_batch`) so rapid-fire texts get a single answer.
- `_generate_and_schedule_reply` is the router; the first step to produce a reply wins, in order: FAQ → unified pre-classifier → STEP 0 multi-intent compose → 0a whole-gallery → 0b specific portfolio piece → 0c portfolio menu → 0d catalogue+prices → 1 photo request → 1b out-of-scope/delay/complaint → 2 service-specific pricing → 2b quote-with-no-product (`_routes_to_onsite_quote`) → 3 full pricing overview → 3b repeated-question → 4 normal `generate_response`. **STEP 2b exists because the quote rule was gated on a priceable intent.** "A quote is delivered at the visit, never as a chat price block" was only ever asked inside STEP 2, so a quote for a WHOLE JOB — which names no product family and classifies as intent 'none' — fell through to STEP 3, where `detect_objection_type` reads the word "quote" as a pricing objection and `_is_genuine_pricing_question` lets the full overview fire: "May I get a quote for a four bedroomed house" came back as the Facebook package plus bathtub prices, a bathroom price list for a whole-house job (prod, barmak 2026-09-05). `_routes_to_onsite_quote` is the counterpart of `_is_genuine_pricing_question` and is asked FIRST — both trigger on the word "quote", only one is the business rule. A confirmed lead is excluded, so the visit is never re-pitched to someone who has booked.
- Outbound goes out on a **1–5 min random delay** via `delayed_response` in a daemon thread; a newer inbound message **cancels the pending send** (`_pending_send_events`) so the batch re-runs with the latest context.

### Unified classifier (`bot/unified_classifier.py`)
- One DeepSeek call returns a dict consumed by all downstream handlers (OOS intent, product/service intent, booking-data extraction, photo/repeat/plan-later flags), replacing ~6 separate calls; on failure it returns `None` and callers fall back to their own classifiers. Access via `uc_as_service_inquiry`, `uc_as_oos_classification`, `uc_is_photo_request`, etc.

### Conversation storage (`bot/models.py` — `Appointment`)
- `conversation_history` is a schemaless `JSONField` of `{role, content, timestamp}` dicts plus optional `message_id`/`quoted`/`media_index` keys — transcript metadata never gets a migration.
- **The transcript holds what was SENT, never the draft of it.** Two layers log an assistant turn: the response mixins log the reply the moment they compose it (~20 call sites, some on paths that never reach the webhook), and the webhook logs the final text at the outbound choke point. Between them sits the whole rewrite chain (memory check, fee + repeat-free-visit strippers, the first-message price note, dash stripping). `add_conversation_message` de-dupes on EXACT content, so while the chain changed nothing the two writes collapsed and nobody noticed; the price note edits the FIRST reply of every conversation, so they stopped matching and the dashboard showed each opener twice, once without the note and once with it, while the lead received only the second (prod 2026-09-03, barmak-plumbing 263786318169). `Appointment.replace_draft_assistant_turns(draft, final_parts)` now drops the draft run and logs the final text; `_generate_and_schedule_reply` captures `_draft_reply` before the chain and calls it instead of appending. A turn already carrying a WAMID was really sent and is never dropped. **Any new step added to that chain is safe automatically; any new outbound path that logs its own reply must go through this helper, not a bare append.**
- Helpers: `add_conversation_message` (logs a turn; back-fills WAMID/quote onto a duplicate entry), `attach_message_id` (stamps an outbound WAMID after the send returns), `record_sent_media` (one entry per image batch carrying `{wamid: description}`), `resolve_quoted_message` (maps an inbound `context.id` → stored text/image description).

### Quoted-reply ("highlighted message") feature
- WhatsApp delivers only the quoted message's **WAMID** (`context.id`), never its text, so outbound WAMIDs are stamped onto history (text in `delayed_response`, images in `send_previous_work_photos` via `record_sent_media`) and resolved locally on the way back.
- The resolved quote is a **separate** `quoted_context` value that reaches classification/LLM calls only — never the rule engine. Before STEP 2, `_generate_and_schedule_reply` re-derives the service intent **deterministically** with `_keyword_product_intent` (the customer's own product word wins, else the quoted caption — e.g. a "rain shower" quote → `shower_cubicle`), so "this one how much?" on a portfolio photo prices the quoted item, not a stale carried-over intent. Deterministic on purpose: the LLM mis-maps short captions (a "rain shower" caption came back `tub_sales`).
- Fragile: resolution coverage is **not universal** — only the two stamping send-paths resolve; messages sent via direct `send_text_message` (plumber alerts, photo intro line, `generate_photo_followup`) and pre-feature history return `None` and silently behave quote-less (signature log: `🔗 … not found in history`). And the quote only steers STEP 2 intent + `generate_response`; the availability/date classifier, FAQ, and booking path don't see it.

### The reasoning controller (`bot/controller.py`, `bot/controller_templates.py`, `bot/visit_slots.py`)
- The model picks the MOVE; deterministic code writes anything the customer must be able to trust. `unified_classify` became **`unified_turn`** (old name kept as an alias) and now returns `reasoning`, `next_move`, `move_confidence` and `state_update.want_level` alongside the classification, on the same call — no extra round-trip.
- **The planning number is `move_confidence`, NOT `confidence`.** That key already means the classification's HIGH/LOW and is read by gates all over the bot; one key with two meanings would have a 0.8 silently answering "is this classification reliable?".
- **Planning failure never degrades classification.** A malformed plan returns the classification with the planning keys stripped. A plan that is entirely ABSENT gets no retry (`planning_attempted`): a missing plan means the prompt is not landing, and retrying every turn would double the call count on the busiest path while fixing nothing. A plan that is present but wrong is a one-off slip and gets exactly one retry.
- **Three gates enforce in code what the prompt only asks for.** `apply_fee_gate` holds `book_visit` back below `want_level='wants_it'`. `apply_plan_path_gate` suppresses it outright once we hold the lead's plan — it reads `plan_status`, never `has_plan`, because `has_plan` goes true when a lead SAYS a plan is coming and a promised plan is nothing to quote from. `work_already_shown` reads `previous_work_photos_sent_at`, never the model's `state_update.work_shown`: the model reports what it believes, the timestamp reports what happened, and when they disagree the gallery goes twice or never.
- `project_next_move` is the deterministic re-projection of signals the classifier already returns. It is both the fallback when the model omits a plan and the BASELINE shadow mode scores the model against. `present_value` projects off a whole-job `quote_request`, **never off a plain `price_ask`** — the visit fee is the only price we volunteer, but a lead who ASKS what a fixture costs still gets the from-price (owner rule, 2026-09-05).
- **Phase 0 (shadow) is live and drives nothing.** Two greppable log lines per turn: `[SHADOW-PLAN]` (what the controller proposed vs what the table projected) and `[SHADOW-BRANCH]` (which branch actually ran, whether they agreed, and `calls=` — the per-turn DeepSeek count, from `services/clients.start_turn_count`). **Phase 2 routing is ON** (`PLUMBOT_CONTROLLER_ROUTING`, default 1, set it to `0` to put everything back on the deterministic order without a deploy; a TEST 0 case asserts the default stays ON, and this paragraph said the opposite for a while after the promotion - read `controller.py` rather than this line if they ever disagree again). `DRIVABLE_MOVES` is `book_visit`, `handle_objection`, `show_work` and `close_pleasantry`; everything else stays with the old router, and all of it goes through `finalise_outbound` like every other send. **Two gates enforce 'the customer's own words outrank the model' for the two moves that would otherwise talk over them**: `close_pleasantry` is held back when `_asks_us_something` or `_booking_half_made`, and `show_work` when `_asks_us_something` **unless the question was a photo request** - "can I see your work?" is the one question whose answer is the work. Barmak 1144 asked "How do l book for a site visit" and got the gallery back, which answers a question they never asked and leaves theirs unanswered.
- **`book_visit` is the close, and the close is made ONCE** (`controller._answering_the_close`). The branch renders `paid_visit_close` and RETURNS before STEP 4 extraction, so once the lead is answering it (this turn carries `extracted.availability` or `datetime_flexible`, or our LATEST message was a visit-time ask), or a booking is half-made or confirmed, the move is held back and the router takes the turn. Driving it there re-pitched a committed lead AND swallowed the slot: barmak 263773380494 said "Yes" and then "Monday 10 am", got the close both times, nothing was stored or booked, and the reply check rewrote the second into "Monday 10 am works. We will come and do the site visit then." (prod, 2026-09-19). `_BOOKING_CLAIM_RE` now also drops a promise to turn up at a named moment ("we will come ... then", "see you Monday"), and a sentence ending in "?" is never treated as a claim. Pinned by the `routing:` and `booking claim:` cases in TEST 0.
- `visit_slots` picks the days, never the model: always tomorrow and the day after, rolled past days the tenant is shut, Shona days for a Shona lead, and "the day after" only when "tomorrow" was actually said first (on a Friday with Saturday closed the first slot is Sunday, and "the day after or Monday" asks the lead to work out the day after what). `proposed_visit_date` is the future-dated equivalent.
- **Copy follows the owner's own voice**, sampled from the 71 `[MANUAL FOLLOW-UP]` staff takeovers in `exports/conversations.jsonl` and written up in `.claude/skills/plumbot-sales-flow/references/house-voice.md`. Short, plain words, one question, no emojis and no dashes — every emoji and dash in that export sits inside a block a staff member PASTED from the bot.

### The outbound chain, and the one step that skipped it
- **`finalise_outbound(reply, appointment, message_body)` is every rewrite a reply gets between composition and the wire**: the reply check, the memory check, **the unbacked-confirmation stripper**, the fee stripper, the repeat-free-visit stripper, the visit-price note and the dash stripper, in that order. It exists because **STEP 0 (multi-intent compose) sent its own reply straight to `delayed_response` and skipped all of it** — so a fee tenant's multi-intent answer could have promised a free visit with nothing to correct it, and no reply from that path was ever de-dashed. Any new send path calls this rather than repeating the chain.
- **We never tell a customer they have an appointment the row does not have** (`strip_unbacked_confirmation`). Whether a booking EXISTS is the biggest of the things the customer must be able to trust, and it was the only one still improvisable by the model. With the booking flow deadlocked (see `_job_is_known`), barmak lead 1144 got "Thursday 3pm works. We'll confirm the visit." straight from DeepSeek, twice, on a row whose status never left `pending` - nothing in the diary, the plumber never told, and the lead back ten hours later asking whether Thursday was real. The stripper drops any SENTENCE claiming a booking exists or promising to make one official, and is **inert on a confirmed lead**, which is what lets the real confirmation copy through untouched (it only ever sends after `status='confirmed'`). **A promise to confirm is treated exactly like a claim of having confirmed** - "we'll confirm" is what a lead reads as "I'm booked", and nothing was running behind it. **A question is never a claim** ("Shall I lock that in?", "Want me to book you a time?"): every pattern is an assertion, or the close itself would be stripped. When the claim was the WHOLE message it is replaced by the true thing, which is also the close. English only on purpose - the Shona close "Ndokubhukira ... here?" is asking PERMISSION to book, and a pattern loose enough to catch a Shona claim catches that ask instead. Pinned by the `booking claim` cases in TEST 0.
- **The proof step honours `retry_count` like every other scripted ask.** `_get_first_pass_question` IS the `retry_count == 0` script and does not check the count itself, so the show_work branch calling it directly re-sent the availability question word for word 60 seconds after the quote route had asked it (barmak 1144, 07:36 and 07:37). Already asked now means the photos ride out with the deterministic `photo_followup` instead. A TEST 0 case asserts no call site in `whatsapp_webhook.py` reaches that script without reading the count first. `show_examples` also counts the images it is actually sending - "Here are a couple" over a single photo is a small lie a customer notices immediately.
- **DeepSeek READS BACK every reply before it is sent** (`bot/response_check.py`, `verify_and_refine`, ON by default via `PLUMBOT_REPLY_CHECK`). It runs FIRST in the chain, on the composed draft, because everything else in the chain is a rule and a rule cannot catch the fault this exists for: a reply that breaks no rule and is still obviously wrong to anyone who read the conversation ("tomorrow or this Tuesday?" to a lead who just said they are out of the country until December - barmak 1005). It is a READER, not a guard: it may only CORRECT, never block, and it is fenced AGAINST the model - no new figure, no new promise word (free / discount / guarantee / mahara), no language change, no growth past 1.6x. A refinement that breaks a fence is REJECTED and logged and the draft still sends, and every failure mode (timeout, bad JSON, refusal) **fails open**. Whatever it returns then goes back through the same deterministic strippers, because a refinement is just another draft and gets no exemption - `ChainOrderTests` pins that ordering. `check=False` skips the READER only, for copy with nothing contextual to get wrong (a fixed template); never pass it for anything the flow composed. **A priced draft may be corrected, never cut down** (`_priced_reply_kept`, 2026-09-22): every figure the draft carries must survive, and so must its closing question, because the price close is deterministic copy. Lead 1161 highlighted a bath-and-shower photo; the draft priced both, the reader kept only the tub and closed on "Want to book a visit?". An unpriced draft is not held to its close. Pinned by the `reply check:` cases in TEST 0.
- **A lead message that never got a reply is answered within the hour** (`bot/unanswered_sweep.py`, owner 2026-09-22). A reply is prepared inside the web server (the batching window, then a delayed send), so a message that lands while a deploy swaps servers is saved and its reply dies with the old server (lead 1161, "How much" at 11:00:10, the new server ready at 11:00:52). On the first tick of each hour the `send_scheduled_followups` command (Email_Follow_Ups cron) finds leads whose latest turns are theirs, 15 minutes to 23 hours old, not paused, inside the free window, and runs them through `_generate_and_schedule_reply` as one batched turn, so every silence and stop rule still applies. The last turn is stamped `sweep_checked` first so a message the pipeline chose to leave (a bare "thank you") is never retried. The cron process exits after the command, so the sweep turns the human reply delay off for itself (`force_immediate_replies`) and waits for the send threads. Pinned by `bot/test_unanswered_sweep.py`.
- **A path that writes to the wire itself must call `_finalised_for_send`.** Most replies reach the customer through `delayed_response`, where the split marker is flattened and every caller has already finalised. **The photo path did neither**: `send_previous_work_photos` sent its lead-in and its follow-up straight to `send_text_message` from its own thread, skipping the ENTIRE chain. The follow-up is the one that bit - it carries the scripted next question, which for `availability_date` IS the availability ask, the exact message `ensure_visit_price_note` exists to attach the call-out fee to - so a fee tenant whose ask rode out behind the photos named no fee and the lead met the figure later, which is the nasty surprise the once-only fee rule was written to prevent. The same gap could promise a free visit for a tenant that charges with nothing downstream to take it back. `_finalised_for_send` runs the chain, flattens the marker, returns '' when the chain decides there is nothing left to say (the caller then sends nothing rather than a draft the chain rejected), and fails open on an unexpected error. The lead-in takes `check=False`, the follow-up the whole chain. `message_body` is threaded through `send_previous_work_photos` so the strippers can still tell an explicit "what does the visit cost?" from an unprompted repeat. Pinned by `PhotoPathGetsTheChainTests`. **Still outside the chain, deliberately:** plumber alerts (not customer copy), the booking confirmation (`send_confirmation_message`, deterministic copy the model must not rewrite) and every cron message - `send_followups` / `send_reminders` get the deterministic strippers via `dequalify_free_visit`, and the post-visit / plan-quote / visit-proposal emails are fixed templates with no model output to read.
- **STEP 0 recorded the priced intents it sent but never checked them.** The single-intent branch has always called `_has_sent_pricing_for_intent`; this one only called `_mark_pricing_intent_sent`. A lead who repeated themselves got the identical price block again (prod, Barmak lead 974, 2026-09-03 13:17 and 13:24, both logged 🧩 Multi-intent compose). It now drops through to the normal flow when every intent it would answer is a price already sent, while a genuinely new question in the mix is still answered.
- **`compose_multi_answer` is English-only** — every snippet, the combined-pricing line and the closer. A Shona lead got an English wall of prices where the single-intent path answers in Shona, so a Shona message now returns None and goes to that path: one answer in their own language beats two in the wrong one. **The scripted first-pass question bank (`_get_first_pass_question`, 13 branches) is English-only too and is NOT yet fixed** — that is why a Shona lead is asked "What area are you in?" in English.

### Supporting classifiers / safety nets
- `faq.py` (no-API canned facts), `out_of_scope_handler.py` (OOS / delay / complaint), `repeated_question_detector.py` (re-asked questions), `semantic_rescue.py` (rescues unclassifiable messages), `service_type_classifier.py` (bathroom / kitchen / new-install), `services/lead_scoring.py` (lead prioritisation).
