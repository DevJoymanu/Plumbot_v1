### Booking, availability, scheduling
- `extraction_mixin` pulls fields (service, area, plan status, name, datetime) and tracks `get_next_question_to_ask`; `availability_mixin` checks business-hours slots and suggests alternatives; `booking_mixin` validates completeness and books; `reschedule_mixin` handles AI-detected reschedules; `plan_upload_mixin` runs "I'll send my plan" flows and plan-status nudges; `notification_mixin` alerts the plumber and optionally Google Calendar.
- **`_job_is_known()` is THE single answer to "do we know enough about the job to book it?"**, read by BOTH `get_next_question_to_ask` (extraction_mixin) and `smart_booking_check` (booking_mixin). They used to disagree: the question order has treated a captured description as answering the service question since 2026-07-02 (a lead who said "2x shower cubicles and accessories" must not be bounced back to the opener), while the booking check went on REQUIRING `project_type`. **A lead carrying only a description therefore had nothing left to be asked AND could never be booked** - unbookable by construction. That is where barmak lead 1144 died (2026-09-09): description and area captured off the opening message (`_build_job_quote_reply` stores a general quote request as the description), "Thursday afternoon, 3pm?" stored as the slot, `ready_to_book` False forever on the missing type. Status stayed `pending`, so there was **no confirmation, no plumber alert and no name ask**, and with the deterministic flow out of questions the turn fell through to the LLM. The DESCRIPTION wins the tie because it is the customer's own account of the job, and everything downstream degrades honestly without a type (`_visit_job_noun` -> "work", `_describe_project_context` -> "the space"). Pinned by the `booking:` cases in TEST 0 and `DescriptionOnlyLeadBooksTests`. **Still open:** that stored description is the lead's REQUEST ("I'd like a quote for some plumbing work"), not an account of the job, and because any non-empty string satisfies `controller.description_captured` the bot never asks what the work actually is.
- **The customer's booking confirmation is queued, not sent inline.** `send_confirmation_message` builds plain conversational copy (`_build_confirmation_message` — no headings, no labelled fields, no emojis, mirroring the lead's language, absent details omitted rather than filled with "Your area") and hands it to `delayed_response` on a daemon thread after `CONFIRMATION_DELAY_MIN/MAX_SECONDS` (45-90s), so it lands like a person writing the details up rather than a receipt printed the moment the row saved — and so the turn is logged and its WAMID stamped. Duplicate sends are blocked by `_claim_confirmation_send`: one conditional UPDATE writes a `[CONFIRMATION_SENT:<slot>]` marker into `internal_notes`, so a repeated "yes" or a second press of the dashboard Confirm button claims nothing, while a genuine reschedule to a new slot still confirms.

### Rescheduling (`reschedule_mixin`)
- Routed from STEP 4 of `generate_response` on a confirmed lead. `detect_reschedule_request_with_ai` (DeepSeek) decides, falling back to the deterministic `detect_reschedule_request` keyword list (English + Shona) when the API is down; `parse_datetime_with_ai` extracts the new slot, `_reschedule_availability` checks it, `process_successful_reschedule` moves it.
- **`_reschedule_slot()` is the single resolver for WHICH appointment moves.** `schedule_job_appointment` keeps ONE row — it flips `appointment_type` and fills `job_scheduled_datetime`, leaving the completed site visit in `scheduled_datetime` — so a confirmed lead can hold two datetimes. Every path (the STEP 4 gate, the detector's quoted time, the availability check, the write, the plumber alert, the email command) goes through it. Before that, a job customer's move was quoted against their old site visit and written to `scheduled_datetime`, while the jobs board and `send_job_reminders` went on reading `job_scheduled_datetime`. A job also checks availability against its own duration (`check_job_availability`), not a single slot.
- `process_successful_reschedule` writes the resolved field, notes the move on the lead with `_append_admin_note` (the old `reschedule_count` / `original_datetime` assignments were guarded by `hasattr` for columns that don't exist, so nothing was ever recorded), then fires the calendar move and `notify_team_about_reschedule`, each best-effort in its own try. **If the save itself fails it returns `_reschedule_breakdown_reply()` — never tell a customer their appointment moved when it didn't.**
- **Three of the methods this flow called never existed** — `notify_team_about_reschedule`, `update_google_calendar_appointment`, `detect_reschedule_request` — and each `AttributeError` was swallowed by the caller's `except`: the plumber was never told, the calendar kept the old slot, and an API blip crashed detection instead of degrading. `add_to_google_calendar` now stores `google_calendar_event_id` so `update_google_calendar_appointment` can PATCH the event (it creates one when no id is on file). A TEST 0 case asserts every method the flow calls is defined — keep phantom calls out.
- Reschedule copy is deterministic (`_build_reschedule_confirmation` / `_build_reschedule_clarification` / `_build_reschedule_unavailable_reply` / `_reschedule_breakdown_reply`): no emojis, mirrors the lead's language, hours via `_hours_clause` (the old fallback hardcoded "8 AM - 6 PM, Monday to Friday" for every tenant), and the breakdown reply offers the tenant's own `plumber_contact()` or no number at all — it used to send every customer to the placeholder "(555) PLUMBING".
- Emailed reschedules go through the same pipeline via `_apply_email_reschedule` in `process_inbound_emails` (availability first; a taken slot moves nothing and asks for another day), so an email move alerts the plumber and updates the calendar exactly like a WhatsApp one.
