Inbound (reply-only), sending identities, transports, the sent-email screens and the Settings > Email health panel.

### The Sent-Emails and Recently-Sent sections showed nothing at all
- **Two independent causes, both "the screen asks a narrower question than the one it is named after".** (1) `sent_email_filters` defaulted to the `dashboard` group - post-visit + quote + site-visit - while **almost no row was TAGGED with one of those categories**: `category` is optional on `send_email_to_recipients` and most senders passed none, so nine of the twelve live rows sat on `other` and were excluded. Measured on prod: barmak's tab showed **0 of 5** rows and homebase's **2 of 7**. Every customer-facing sender now passes one (`booking`, `reminder`, `delay`, `quote_followup`, and a new `followup` for the staff-queued send), the `followup` and `plumber` groups gather what the old set could not name, and **the default is now `all`** - a tab called "Sent Emails" that shows a third of the email we sent is worse than no tab, because it gets believed. The narrow set is still one chip. (2) The Emails tab's "Recently Sent" read conversation-history MARKERS, of which only three are email (`[DELAY LAST CHECK]`, `[SCHEDULED EMAIL]`, `[EMAIL FOLLOW-UP]` - and nothing anywhere writes the last one), two of those written solely by a staff-queued send; so every automated email was invisible. It reads `SentEmail` now - the row written at the one send choke point - workspace-scoped and inside the same window, and links to the stored copy.
- **A send blocked by the tenant's outbound-email switch is RECORDED as failed.** `email_sending_enabled` returns before the send and used to return before the logging too, so a tenant with the switch off (**the default for every tenant but the homebase seed**) showed an empty tab indistinguishable from a tenant with no mail to send - the one state a screen about sent email must not be ambiguous about. A `--dry-run` still records nothing. Pinned by `FollowupEmailSectionsTests`.

### Email
- **Inbound: the bot answers email too** (`process_inbound_emails`, 5-min cron), but **EMAIL IS REPLY-ONLY: it answers only people already in the system with a WhatsApp record, and no email ever creates a lead** (2026-08-24 rule; cold-email intake and its `INBOUND_LEAD_ADDRESSES` address->tenant routing were removed). A reply on a thread we started is matched by the `<apt-{id}.…>` Message-ID (or a legacy `[APT-{id}]` subject tag); an email with no thread reference is matched to a lead by `customer_email` (`_known_lead_for_sender`, most recently updated wins, subject folded into the customer's turn since off-thread the subject often IS the request). Either way the matched lead must pass `_is_whatsapp_lead` — a real phone number, not a synthetic `email_…` (legacy cold-email row) or `quotation_only_…` key — so the check is about the LEAD, not about how the mail matched. Everything else (receipts, support tickets, strangers writing in cold) belongs to nobody in the CRM and is left UNREAD for a human. No routing is needed for multi-tenancy: the matched lead carries its own tenant. **Two gates sit in front of the rule** (the polled inbox is the operator's personal Gmail, so the bot once opened leads on Stripe receipts and replied to them): (1) `_is_our_own_mail` drops our own traffic BEFORE the thread tag is trusted — the polled address, `DEFAULT_FROM_EMAIL`, every tenant `customer_from_email`/`email_sender`, `PLATFORM_NOTIFICATION_EMAIL`, `PLUMBER_NOTIFICATION_EMAILS`, the owner accounts, and anything on `PLATFORM_EMAIL_DOMAIN`; the Bcc copy of our own customer email carries the same `[APT-{id}]` reference the customer's reply does, so an APT match alone is not proof a customer wrote. (2) `_is_automated` drops machine mail (Auto-Submitted / List-Id / X-Autoreply headers, no-reply & mailer-daemon & receipt/billing/stripe addresses, bounce/out-of-office/receipt subjects) — without that guard the bot email-loops. Mail the bot declines is left **UNREAD** and its body is never downloaded: fetches use `BODY.PEEK` (`_fetch_unseen_headers` → gates → `_fetch_message`), because a plain `RFC822` fetch silently marks the operator's own mail read. Any new mailbox-touching code must keep the peek-then-gate order. A `--dry-run` neither replies nor marks anything seen.
- Email-only leads have no phone number, so they are excluded from proactive WhatsApp: `send_followups` skips `email_`/`quotation_only_` prefixes and `send_reminders._send_wa` refuses any non-numeric recipient. Any new synthetic-key lead type must do the same.
- **Two sending identities per tenant** (`bot/plumber_notifications.py`): `tenant_platform_from_email` → `<tenant-slug>@notifications.homexmedia.com` (`PLATFORM_EMAIL_DOMAIN`) is used for **internal** alerts — the mail to the operator and to the tenant's own inbox; `tenant_customer_from_email` → the tenant's own domain address (`TenantProfile.customer_from_email`, set on the Profile page) is used for **everything the tenant's clients receive**, falling back to that platform sender when unset, and to `DEFAULT_FROM_EMAIL` only for tenant-less platform mail (password resets). Resolution happens once at the `send_email_to_recipients` choke point and is threaded to all three transports as `from_email`/`reply_to`; only `send_plumber_notification_email` passes an explicit `from_email`. Reply-To follows From on any tenant-scoped send, so a customer's reply reaches the tenant, never the platform inbox. **One shared authenticated domain with a per-tenant local part — deliberately not a subdomain per tenant: every distinct domain needs its own SPF/DKIM records and consumes one of Brevo's authenticated-domain slots (the account is on the free tier). DNS: `notifications.homexmedia.com`, and any tenant domain, must be SPF/DKIM-authenticated in Brevo before it delivers.** Note `email_sender` is a recipient inbox, `customer_from_email` a sending identity — never conflate them.
- Customer/transactional email goes through the **SendGrid v3 HTTP API (port 443)** in `bot/plumber_notifications.py` (`_send_via_sendgrid`); Railway blocks all outbound SMTP, so the legacy `IPv4SMTPBackend` (`bot/email_backends.py`) is a fallback only. SendGrid click/open tracking is disabled to keep `tel:`/`wa.me` links clean. HTML lives in `bot/customer_emails.py`; subjects carry `[APT-{id}]` so IMAP replies match back to the appointment.

### Settings > Email: can the bot send, read and answer mail? (`bot/email_health.py`)
- **Three capabilities, because they fail independently.** SENDING needs a transport (Brevo, else SendGrid; **SMTP alone reads BLOCKED** - Railway blocks outbound SMTP, so calling it ready would be a green tick over a dead path) plus a from-identity, AND the per-tenant `platform_flags.email_sending_enabled` switch, which **defaults OFF for every tenant but the homebase seed** and is the likeliest reason a tenant's email is silently absent. That switch is its own line and its own state (`partial`), never folded into the transport verdict: a good transport and a closed switch are two problems with two fixes. RECEIVING needs `IMAP_EMAIL` + `IMAP_PASSWORD`. ANSWERING needs `DEEPSEEK_API_KEY` **and** receiving, because a reply is only ever an answer to mail we read. `email_capabilities(tenant)` is the single reader and the page adds no logic of its own.
- **CONFIGURATION IS NOT PROOF and the copy says so.** Nothing here can tell a dead cron from a quiet one (that needs the Railway deployment metadata - see `_cronScheduleTrap`), so the panel states what is configured and each test states what it actually proves.
- **Seeing is for every superuser; TESTING is adminJ's alone.** Each test performs a real action, so `email_health_test` is `@owner_required` + `@require_POST` and re-checks server-side - hiding a button is presentation, not permission, and a GET that sends email is one a browser can prefetch. The page itself stays `@superuser_required` like the rest of Settings (platform config, not a tenant control), so "everybody else" means the other superusers; if tenants ever need to see this, mirror the read-only panel on the Profile page rather than relaxing this gate.
- **The send test goes to the operator's OWN address** (`_email_test_address`: their login email, else `PLATFORM_NOTIFICATION_EMAIL`) and is deliberately not a free-text field - a settings page that emails anything you type is a relay for whoever holds the account. It sends with `tenant=None` (platform mail), so a green result can never be read as overriding a tenant's switch.
- **The receive test opens the mailbox READONLY and fetches nothing.** The polled inbox is the operator's own Gmail and the whole inbound pipeline peeks so that looking never marks their mail read; a test that downloaded a body would break that rule from the other side. Asserted: `select('INBOX', readonly=True)`, no `fetch`, no `store`.
- **`_env` reads a setting by PRESENCE, not truthiness.** Every transport key is declared in settings.py via `os.environ.get`, so an explicit `@override_settings(BREVO_API_KEY='')` must mean empty rather than "go and look at the real environment" - that fallback made a blocked-transport case read as ready on any machine with a key exported. Names settings.py never declares (the `IMAP_*` group, read straight from the environment by the cron) still fall through. Pinned by `EmailHealthPanelTests` and `EmailHealthResolverTests`.
