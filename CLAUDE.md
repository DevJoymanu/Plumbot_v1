# Plumbot – Claude Code Instructions

## Project Overview
Plumbot is a WhatsApp-based appointment scheduling and sales chatbot for Homebase Plumbers in Harare, Zimbabwe. It is built with Django, deployed on Railway, uses Twilio for WhatsApp messaging, and DeepSeek API for AI-powered intent classification and response generation.

## Core Files
- `whatsapp_webhook.py` / `views.py` — main conversation flow logic
- `send_followups.py` — Railway cron job for follow-up scheduling
- DeepSeek API integration — intent classification and response generation

## Coding Rules
- Never introduce new dependencies unless explicitly asked
- Reuse existing infrastructure and patterns already in the codebase
- Always preserve WAMID deduplication logic — never remove it
- Exit-signal detection must always run before any flow-stage logic
- Never re-pitch the site visit to a customer who has already committed

## Conversation Flow Logic
Plumbot uses Hormozi's four-stage qualification framework:
1. **Value** — lead with what we offer and why it matters
2. **Price** — be upfront about pricing before heavy qualification
3. **Qualification** — ask targeted questions using "this or that" framing
4. **Close** — use presumptive closes and micro-yes ladders

When editing flow logic:
- Customers may respond with partial answers (e.g. just a day name like "Sunday") — always handle fuzzy/partial date-time inputs gracefully
- Support both English and Shona responses
- Avoid bot loops — if a question has already been asked, do not repeat it
- Use the semantic duplicate question detector before sending any qualification question

## DeepSeek API Integration
The DeepSeek API is used for intent classification and response generation. When improving prompts or API calls:
- Embed step-by-step reasoning instructions in the system prompt
- Instruct the model to identify customer intent before selecting a response
- Use chain-of-thought style prompting: interpret → consider alternatives → select stage → respond
- Keep responses short, warm, and conversational — like a knowledgeable colleague texting

## System Prompt for DeepSeek
When generating or editing the DeepSeek system prompt, use this as the base:

---
You are Plumbot, a WhatsApp sales and scheduling assistant for Homebase Plumbers in Harare, Zimbabwe. Before every response, reason through the following steps internally:

1. **Intent** — What is the customer actually asking or signaling? Look beyond the literal words.
2. **Stage** — Which of the four stages are they in: value, price, qualification, or close?
3. **Ambiguity** — Is their message unclear or partial (e.g. just a day name, a one-word reply)? If so, clarify gently without repeating yourself.
4. **Commitment signals** — Are they showing readiness to book? If yes, move to close immediately.
5. **Exit signals** — Are they trying to leave the conversation? If yes, acknowledge gracefully and leave the door open.

Then respond:
- In the same language they used (English or Shona)
- Warmly and conversationally — never robotic
- Concisely — WhatsApp messages, not essays
- With presumptive framing — offer choices, not yes/no questions
- Leading with value and confidence, not desperation
---

## Common Bugs to Watch For
- Bot re-pitching site visit after customer already agreed → check commitment state before sending pitch
- Price queries falling through to wrong flow stage → classify price intent before stage routing
- Duplicate messages → always check WAMID before processing
- Follow-up cron skipping eligible leads → check lead eligibility filter logic carefully
- Flow not advancing on partial date inputs → normalise day names to full date-time before validation

## Current State

Orientation for the next session: what the system does today, why it's built this way, what's fragile, and the conventions to keep. Reflects the codebase as of June 2026.

### Stack & composition
- Django app `bot/` on Railway; WhatsApp via Twilio/Meta Cloud API; all AI via **DeepSeek** through the OpenAI SDK pointed at `api.deepseek.com`.
- The shared DeepSeek client (`bot/services/clients.py`) monkey-patches `chat.completions.create` to **force "thinking" mode off on every call** — thinking mode ate the `max_tokens` budget and returned empty/truncated JSON, breaking every classifier (`DEEPSEEK_THINKING=enabled` reverts).
- `Plumbot` (`bot/views/plumbot/`) is one class composed from mixins — `state`, `response`, `extraction`, `availability`, `booking`, `reschedule`, `notification`, `plan_upload`; `base.py` wires them and `get_or_create`s the `Appointment` per phone number.

### Inbound pipeline (`bot/whatsapp_webhook.py`)
- `process_message_change` → `handle_text_message(sender, text, message_id, quoted_id)` logs the user turn, resolves any quoted reply, then **debounce-batches per sender** (`_enqueue_for_response` / `_flush_text_batch`) so rapid-fire texts get a single answer.
- `_generate_and_schedule_reply` is the router; the first step to produce a reply wins, in order: FAQ → unified pre-classifier → STEP 0 multi-intent compose → 0a whole-gallery → 0b specific portfolio piece → 0c portfolio menu → 0d catalogue+prices → 1 photo request → 1b out-of-scope/delay/complaint → 2 service-specific pricing → 2b quote-with-no-product (`_routes_to_onsite_quote`) → 3 full pricing overview → 3b repeated-question → 4 normal `generate_response`. **STEP 2b exists because the quote rule was gated on a priceable intent.** "A quote is delivered at the visit, never as a chat price block" was only ever asked inside STEP 2, so a quote for a WHOLE JOB — which names no product family and classifies as intent 'none' — fell through to STEP 3, where `detect_objection_type` reads the word "quote" as a pricing objection and `_is_genuine_pricing_question` lets the full overview fire: "May I get a quote for a four bedroomed house" came back as the Facebook package plus bathtub prices, a bathroom price list for a whole-house job (prod, barmak 2026-09-05). `_routes_to_onsite_quote` is the counterpart of `_is_genuine_pricing_question` and is asked FIRST — both trigger on the word "quote", only one is the business rule. A confirmed lead is excluded, so the visit is never re-pitched to someone who has booked.
- Outbound goes out on a **1–5 min random delay** via `delayed_response` in a daemon thread; a newer inbound message **cancels the pending send** (`_pending_send_events`) so the batch re-runs with the latest context.

### Unified classifier (`bot/unified_classifier.py`)
- One DeepSeek call returns a dict consumed by all downstream handlers (OOS intent, product/service intent, booking-data extraction, photo/repeat/plan-later flags), replacing ~6 separate calls; on failure it returns `None` and callers fall back to their own classifiers. Access via `uc_as_service_inquiry`, `uc_as_oos_classification`, `uc_is_photo_request`, etc.

### Conversation storage (`bot/models.py` — `Appointment`)
- `conversation_history` is a schemaless `JSONField` of `{role, content, timestamp}` dicts plus optional `message_id`/`quoted`/`media_index` keys — transcript metadata never gets a migration.
- **The transcript holds what was SENT, never the draft of it.** Two layers log an assistant turn: the response mixins log the reply the moment they compose it (~20 call sites, some on paths that never reach the webhook), and the webhook logs the final text at the outbound choke point. Between them sits the whole rewrite chain (memory check, fee + repeat-free-visit strippers, the first-message price note, dash stripping). `add_conversation_message` de-dupes on EXACT content, so while the chain changed nothing the two writes collapsed and nobody noticed; the price note edits the FIRST reply of every conversation, so they stopped matching and the dashboard showed each opener twice, once without the note and once with it, while the lead received only the second (prod 2026-09-03, barmak-plumbing 263786318169). `Appointment.replace_draft_assistant_turns(draft, final_parts)` now drops the draft run and logs the final text; `_generate_and_schedule_reply` captures `_draft_reply` before the chain and calls it instead of appending. A turn already carrying a WAMID was really sent and is never dropped. **Any new step added to that chain is safe automatically; any new outbound path that logs its own reply must go through this helper, not a bare append.**
- Helpers: `add_conversation_message` (logs a turn; back-fills WAMID/quote onto a duplicate entry), `attach_message_id` (stamps an outbound WAMID after the send returns), `record_sent_media` (one entry per image batch carrying `{wamid: description}`), `resolve_quoted_message` (maps an inbound `context.id` → stored text/image description).

### Quoted-reply ("highlighted message") feature
- WhatsApp delivers only the quoted message's **WAMID** (`context.id`), never its text, so outbound WAMIDs are stamped onto history (text in `delayed_response`, images in `send_previous_work_photos` via `record_sent_media`) and resolved locally on the way back.
- The resolved quote is a **separate** `quoted_context` value that reaches classification/LLM calls only — never the rule engine. Before STEP 2, `_generate_and_schedule_reply` re-derives the service intent **deterministically** with `_keyword_product_intent` (the customer's own product word wins, else the quoted caption — e.g. a "rain shower" quote → `shower_cubicle`), so "this one how much?" on a portfolio photo prices the quoted item, not a stale carried-over intent. Deterministic on purpose: the LLM mis-maps short captions (a "rain shower" caption came back `tub_sales`).
- Fragile: resolution coverage is **not universal** — only the two stamping send-paths resolve; messages sent via direct `send_text_message` (plumber alerts, photo intro line, `generate_photo_followup`) and pre-feature history return `None` and silently behave quote-less (signature log: `🔗 … not found in history`). And the quote only steers STEP 2 intent + `generate_response`; the availability/date classifier, FAQ, and booking path don't see it.

### Portfolio / catalogue (`bot/portfolio_catalog.py`)
- Static list of previous-work pieces (title, "from" price, description, keywords). `match_portfolio_item` returns a single item only when the message clearly references one piece, else `None` → whole-gallery send; `_describe_work_image` derives a per-image description (curated title for catalogued files, tidied filename otherwise) for the media index. Prices are the business's own "from" rates from `bot/sales_profiles/homebase.md` (source of truth — keep in sync, never invent figures); captions are title-only.

### Pricing & sales (`bot/views/plumbot/response_mixin.py`)
- `detect_service_inquiry` → priceable intent; `handle_service_inquiry(intent, message)` builds the reply from a `structured_pricing` table keyed by intent (the message is used only for language detection). `generate_pricing_overview` gives the full menu; `compose_multi_answer` answers 2+ info questions in one reply.
- Pricing is gated: don't volunteer price when unasked, don't re-send an already-sent intent, and don't price a message that's a project description / booking-capture answer.

### Booking, availability, scheduling
- `extraction_mixin` pulls fields (service, area, plan status, name, datetime) and tracks `get_next_question_to_ask`; `availability_mixin` checks business-hours slots and suggests alternatives; `booking_mixin` validates completeness and books; `reschedule_mixin` handles AI-detected reschedules; `plan_upload_mixin` runs "I'll send my plan" flows and plan-status nudges; `notification_mixin` alerts the plumber and optionally Google Calendar.
- **The customer's booking confirmation is queued, not sent inline.** `send_confirmation_message` builds plain conversational copy (`_build_confirmation_message` — no headings, no labelled fields, no emojis, mirroring the lead's language, absent details omitted rather than filled with "Your area") and hands it to `delayed_response` on a daemon thread after `CONFIRMATION_DELAY_MIN/MAX_SECONDS` (45-90s), so it lands like a person writing the details up rather than a receipt printed the moment the row saved — and so the turn is logged and its WAMID stamped. Duplicate sends are blocked by `_claim_confirmation_send`: one conditional UPDATE writes a `[CONFIRMATION_SENT:<slot>]` marker into `internal_notes`, so a repeated "yes" or a second press of the dashboard Confirm button claims nothing, while a genuine reschedule to a new slot still confirms.

### Rescheduling (`reschedule_mixin`)
- Routed from STEP 4 of `generate_response` on a confirmed lead. `detect_reschedule_request_with_ai` (DeepSeek) decides, falling back to the deterministic `detect_reschedule_request` keyword list (English + Shona) when the API is down; `parse_datetime_with_ai` extracts the new slot, `_reschedule_availability` checks it, `process_successful_reschedule` moves it.
- **`_reschedule_slot()` is the single resolver for WHICH appointment moves.** `schedule_job_appointment` keeps ONE row — it flips `appointment_type` and fills `job_scheduled_datetime`, leaving the completed site visit in `scheduled_datetime` — so a confirmed lead can hold two datetimes. Every path (the STEP 4 gate, the detector's quoted time, the availability check, the write, the plumber alert, the email command) goes through it. Before that, a job customer's move was quoted against their old site visit and written to `scheduled_datetime`, while the jobs board and `send_job_reminders` went on reading `job_scheduled_datetime`. A job also checks availability against its own duration (`check_job_availability`), not a single slot.
- `process_successful_reschedule` writes the resolved field, notes the move on the lead with `_append_admin_note` (the old `reschedule_count` / `original_datetime` assignments were guarded by `hasattr` for columns that don't exist, so nothing was ever recorded), then fires the calendar move and `notify_team_about_reschedule`, each best-effort in its own try. **If the save itself fails it returns `_reschedule_breakdown_reply()` — never tell a customer their appointment moved when it didn't.**
- **Three of the methods this flow called never existed** — `notify_team_about_reschedule`, `update_google_calendar_appointment`, `detect_reschedule_request` — and each `AttributeError` was swallowed by the caller's `except`: the plumber was never told, the calendar kept the old slot, and an API blip crashed detection instead of degrading. `add_to_google_calendar` now stores `google_calendar_event_id` so `update_google_calendar_appointment` can PATCH the event (it creates one when no id is on file). A TEST 0 case asserts every method the flow calls is defined — keep phantom calls out.
- Reschedule copy is deterministic (`_build_reschedule_confirmation` / `_build_reschedule_clarification` / `_build_reschedule_unavailable_reply` / `_reschedule_breakdown_reply`): no emojis, mirrors the lead's language, hours via `_hours_clause` (the old fallback hardcoded "8 AM - 6 PM, Monday to Friday" for every tenant), and the breakdown reply offers the tenant's own `plumber_contact()` or no number at all — it used to send every customer to the placeholder "(555) PLUMBING".
- Emailed reschedules go through the same pipeline via `_apply_email_reschedule` in `process_inbound_emails` (availability first; a taken slot moves nothing and asks for another day), so an email move alerts the plumber and updates the calendar exactly like a WhatsApp one.

### Follow-ups & cron (`bot/management/commands/`)
- `send_followups` — **FOUR follow-ups for EVERY lead. What a lead's window changes is WHERE the four sit, never how many** (owner rule, 2026-09-03). On a full 72h window they take the band placement: **2 in the first 24h, 1 in 24-48h, 1 in 48-72h**, measured from the lead's last message — `FOLLOWUP_BAND_OFFSETS` as absolute hours per temperature (COLD 6/13/33/60h, VERY_HOT 4/10/27/51h), with `FOLLOWUP_BANDS` the contract in data and TEST 0 asserting every tuple against it. **Temperature moves a touch WITHIN its band, never into another one.** **Only a 72h window can carry that placement** — a touch written for 33h could only ever bounce with 131047 on a window that shut at 24h — so any shorter window (a standard lead, or an ad lead who replied with most of the 72h spent) gets `SHORT_WINDOW_FRACTIONS` instead: the same four touches as a share of the usable span (24h COLD ≈ 3.6/8.6/13.5/18.9h, 48h left ≈ 7.4/17.7/27.9/39.1h). Fractions rather than a second hour table, so one branch covers every window length. `followup_offsets_for(lead)` is the resolver and picks the branch on `bands[-1] <= usable_window_hours`; **the count is read off it** — `max_followups_for` is `len(followup_offsets_for(lead))`, so cron retirement, the UI chip, the dashboard due-list and the LLM prompt cannot disagree with the schedule, and `FOLLOWUP_MIN_COUNT` = 4 is the run length (also the delay/parked nudge target). Absolute offsets mean a touch deferred by the nightly contact window cannot push the later ones past the close — the old cumulative cadence (COLD 4+6+6+6 = 22h + jitter) overshot the 24h window and silently retired leads on three. **A reply resets the counter to zero** (`Appointment.reset_followup_sequence`, called from `mark_customer_response` and from the emailed-reply stamp in `process_inbound_emails`): the run is four touches SINCE THEY LAST SPOKE, so a lead who answers is never retired, and a reply revives one the cron already retired since it reopens the window too. It sets fields only — the caller saves. `last_followup_sent` is deliberately NOT cleared: it is the durable "have we ever chased this lead" record (the webhook's `mid_conversation` check reads it, since the counter no longer survives a reply). **Ad leads no longer get a bigger COUNT** — the old six-touch `CTWA_FOLLOWUP_OFFSETS` / `has_extended_window` path is gone; the longer window buys spacing, not extra messages. **Placement is reconciled with SENDABLE hours** — the messaging window intersected with `CONTACT_WINDOWS` (12:33–13:57 and 16:03–18:30, two windows, every day, half-open so the last send in each is 13:56 and 18:29, SAST — owner rule, 2026-09-05): the sendable span no longer shortens the SCHEDULE (`_sendable_hours` and `MIN_SENDABLE_SPAN_HOURS` are gone — shrinking the span dropped a whole touch where moving it would do), instead `_scheduled_due_at` rolls a due moment forward out of the quiet hours and, when that roll would land after the window has shut, pulls it BACK to `_last_sendable_moment` minus `LAST_CALL_GRACE_MINUTES` (`_window_moment_before` is the mirror of `_next_window_open`). Without that pull-back a touch due at 02:00 on a window closing at 06:00 waited for 08:21, by which time free-form sending was dead — so it only reached the lead when they messaged again, arriving as a stale nudge on top of their live message. On a last call the spacing relaxes to `LAST_CALL_MIN_GAP_HOURS`. Two guards keep a touch off a live exchange: `FOLLOWUP_LIVE_CONVERSATION_MINUTES` (the lead just wrote — the bot's own reply is the touch; this also replaces the old 2-minute eligibility prefilter) and `FOLLOWUP_QUIET_AFTER_OUTBOUND_HOURS` (we just wrote). The delay-ghost and parked nudge loops share the last-call rule via `_is_last_call`. Delay-flow and parked nudges use the same rule (`_DELAY_NUDGE_FRACTIONS`, `_PARKED_NUDGE_FRACTIONS`) and also do 4 — parked nudges moved from 3/7 DAYS (always outside the window, so every one bounced 131047) into the back half of the window. A closed window still blocks everything: we never pay for templates. Other Railway crons: `send_reminders`, `send_job_reminders`, `summarize_unconfirmed_leads`, `process_inbound_emails`, `send_scheduled_followups`. **Every service in the Railway project shares the repo's `railway.json`, whose `deploy.startCommand` overrides each service's own** — so all of them boot `start.sh`, which runs `manage.py <job>` when `PLUMBOT_CRON` is set (comma-separated for a service carrying several jobs) and gunicorn when it isn't. Adding a cron = new service + `cronSchedule` + a `PLUMBOT_CRON` value, never a start command in the dashboard (it would be overridden). The `_cronsReference` block in `railway.json` documents the current mapping (services: `Follow_Ups`, `Reminders`, `Email_Follow_Ups`, and the `Plumbot_v1` web role); Railway does not read it. **A Railway deployment bakes in the cron schedule the service had when that deployment was created.** One built while the schedule was absent comes out `buildOnly=false` / `cronSchedule=null`: it runs `start.sh` once at deploy time and never ticks again, while the service page still shows the schedule and Railway keeps advancing `nextCronRunAt` — silent, with the deployment sitting at SUCCESS. That stopped `send_followups` dead from 2026-08-25 to 2026-08-28; the only follow-ups sent in between came from a human pressing the dashboard's manual follow-up check (`manual_followup_check`), which runs the command inside the WEB service. `railway redeploy` does not fix it — it replays the bad snapshot; re-apply the schedule (`serviceInstanceUpdate`) then deploy fresh (`serviceInstanceDeployV2`). To check a cron service is genuinely alive, read its latest deployment meta (`buildOnly` true, `serviceManifest.deploy.cronSchedule` set) and confirm its `deploymentLogs` carry one `[start.sh] cron job` line per tick — the DB alone cannot tell a dead cron from a quiet one. See `_cronScheduleTrap` in `railway.json`. (`notify_priority_leads` — the daily plumber WhatsApp alert — was removed 2026-07-08; the priority-leads dashboard pages remain.)

### Post-visit debrief + quote follow-ups (`bot/post_visit.py`)
- Everything after a site visit hangs off **one row, `SiteVisitReport`** (OneToOne on the lead, migration 0077), and **one tokenized URL**. Two entry points open that same URL: the **in-app banner pinned at the very top of the appointment detail screen** ("Is the site visit complete?" → `site_visit_start`, staff-only, creates the row then redirects). **It replaced the old `complete_site_visit` view, URL and template, which are deleted** — that button sat buried in the Scheduling card and wrote `site_visit_notes` / `plumber_assessment` with no quote and no follow-ups behind it. There is now ONE way to log a visit. The banner is **always rendered and never gated on the row looking tidy** (not on `status='confirmed'`, not on a past slot): plenty of real visits happen without the bot ever pinning a slot, and gating the only control on that made those impossible to log. `_site_visit_banner` returns `{'state': 'open'}` or `{'state': 'resolved', 'report': ...}` — once logged it reports the outcome and what it set running rather than vanishing, so it is never a dead control. `is_due_for_report` still gates the CRON (an unscheduled lead has no visit-end to measure 35 minutes from); only the UI is ungated and the **fallback email to the plumber 35 minutes after the visit ends** (`send_site_visit_form_email`). One URL and one `submitted_at` is what makes the form single-use ACROSS both paths: `apply_submission` is the only writer of that timestamp and refuses a second call, and the cron stops sending the fallback the moment it is set. The form is deliberately **public, token-only** (`/site-visit/<token>/`, added to `TenantMiddleware._EXEMPT_PREFIXES`) — the plumber taps it from an email on their phone with no session; the token is a uuid4 and the row is single-use, so the link is the credential. Anything needing real authority (creating the quote) redirects to a staff-gated screen.
- **The outcome radio is the gate.** Only `went_ahead` reveals the questions and the Create Quote button; `no_show` / `rescheduled` / `not_proceeding` submit straight through to `_route_other_outcome` (no quote, no sequence, `sequence='stopped'`) and write the lead state the rest of the dashboard reads — `no_show` sets status, `rescheduled` returns it to pending for the reschedule screen, `not_proceeding` sets `is_lead_active=False`, which is the flag every follow-up path already honours. `went_ahead` requires an email (the form is the ONLY place a missing one can be added) and marks the visit complete on the lead.
- **Job notes carry into the quote screen.** `CreateQuotationView` puts the report's notes in `quote_prefill_notes`, and `create_quotation.html` renders them with `data-prefilled="1"` — `loadAppointmentData` checks that flag before writing `projectNotes`, or its `project_description` fetch would blank what the plumber typed on site. The sectioned layout does not take them: its `notes` are the payment terms, not a description.
- **Send is on the EDITOR and independent of Save.** Both buttons are always enabled; each runs `persist()` first (save, then send), so the plumber never has to press Save and what the customer gets is the quote on screen. `currentQuotationId` is filled by the first save, so a second send updates the same row rather than raising another (Download and Delete follow it too).
- **The PDF follows the TENANT's layout, like every screen does** (`bot/quote_pdf.py`). One renderer served everybody, so a sectioned tenant's customers received a flat list with none of their sections, subtotals, VAT, terms, banking or signature line — a document nothing like the one their plumber approved. `build_quotation_pdf` now branches on the same `is_sectioned(tenant)` the screens use: `_flat_sheet` mirrors `quote_flat_document.html`, `_sectioned_sheet` mirrors `quote_sectioned_view.html` + `quote_footer.html`. The sectioned renderer takes its colours and proportions straight from `quote_sectioned_css.html` (`SEC` / `SEC_COLS`): a **two-column letterhead** (mark and name left in `--bq-blue`, contacts right in `--bq-teal`), the green `t / a` rule, a centred red underlined "Quotation", and a green-ruled table led by **QTY | DESCRIPTION | UNIT PRICE | TOTAL PRICE** — the sheet's own order, not Item-first. It is **ONE table** with the section headings as rows, so the column header is drawn once and repeats only on a page break. Text wraps to a MEASURED width (`_wrap_px`, via `canvas.stringWidth`): a character count put Barmak's services blurb past the right margin, where the customer's copy cut it mid-word. Markup cannot be shared between HTML and a reportlab canvas, so `QuotePdfMatchesTheAppTests` asserts the FIGURES and blocks agree, and **`QuotePdfGeometryTests` asserts WHERE things land** — name left, contacts right, columns in order, header drawn once, nothing past the right margin — by reading the drawing coordinates out of the content stream (which reportlab writes ASCII85 **and** flate-compressed, so both layers come off first). It also fixes a hardcoded `US$` on every tenant's figures, and prints the ITEM LINES rather than the double-counted `materials_cost` column.
- **`strapline` was never a letterhead key.** `TenantConfig.letterhead()` exposes `services_blurb` / `maintenance_blurb` / `tagline`; the flat letterhead partial and the PDF both asked for `lh.strapline`, so that line silently never rendered. Read the schema in `letterhead()` before adding a key to a quote document.
- **The PDF really is attached, via the Web Share API.** `navigator.share({files:[pdf]})` hands WhatsApp the actual file; the plumber picks the chat and sends. Two routes, because the platform gives us two and neither does everything: **share preselects the FILE but the OS owns the contact picker**, and **a wa.me link preselects the CHAT but no link of any kind can carry a file**. Both are offered, whichever the device supports leading. The blob is fetched on page LOAD, not on click — `navigator.share` must run inside the gesture that triggered it, and awaiting a fetch first spends that gesture (Safari throws `NotAllowedError`). The button stays `hidden` until `canShare({files})` passes against the REAL file, so a desktop never gets a control that throws on tap; an `AbortError` (share sheet closed) is not reported as a failure. Exercised in Node against both device shapes.
- **Every WhatsApp send control in the app is `quotation_whatsapp_handoff`** — the quotes list, both quote pages, the appointment's Quotes tab, and the editor (which saves, then navigates there). It downloads the PDF, shows the message and opens the chat on the plumber's own number; **the bot never sends the quote**. `send_quotation` (the Cloud API document send) still works but is deliberately linked from no screen.
- **WhatsApp hands off to the plumber's OWN app.** The button downloads the PDF and opens `wa.me/<lead digits>` with a prefilled line, so the quote comes from the number the customer already knows and the **24h messaging window that limits the bot's own sends does not apply** (a quote often goes out days after the visit, when a Cloud API document send would 131047). **A wa.me link and a `mailto:` draft carry TEXT only — neither can attach a file** — which is why the PDF is downloaded first, via a hidden iframe so the page stays put. The handoff window is opened synchronously inside the click and pointed at the URL after the save resolves, or the popup blocker eats it.
- **Email offers both routes every time**, with the tenant's `TenantProfile.quote_email_mode` (migration 0080, set on the Profile page) deciding only which is pre-marked `Default`: `platform` sends now from the configured address with the PDF attached, `manual` downloads the PDF and opens a `mailto:` draft in the plumber's own app. The choice is a default, never a restriction.
- **`mark_quotation_sent` records a handoff.** The server never sees a message sent from the plumber's own app, so without it the quotes list would read "Not sent" forever on those routes. It records what the plumber DID, and the conversation note says "handed to the plumber to send" rather than claiming delivery.
- **The two quote-send buttons are independent.** `send_quotation` (WhatsApp, `sent_via_whatsapp`) and `send_quotation_email` (email + the same `build_quotation_pdf_file` PDF, `sent_via_email`) each keep their own flag, neither is hidden after use, and **neither has any bearing on the follow-up channel, which is always email** — email is the address the form always captures, so it is the only reliable automated channel.
- **The scheduler is `run_post_visit_tick`** (command `send_post_visit_followups`, riding the existing `Email_Follow_Ups` service at */5). Three branches, all idempotent because every send is gated by the timestamp written as it goes out: **Case A** — a specific date on file gets ONE confirmation two days before at 09:00, then `sequence='done'`; **Case B** — a rough timeframe or "didn't say" gets ask #1 next day at noon, #2 three days later, #3 seven days after that, then cold + `mark_handed_off` + `send_post_visit_handback_email`; **Case C** — no form by noon the next day is treated as "no date, lead has email" and starts Case B directly, and with no email on file hands the lead back instead (once, gated by `no_email_notified_at`). **Case C leaves the form OPEN**, so its branch is re-entered every tick and must start the sequence exactly once — the `sequence != 'awaiting_form'` early-out is what stops the next tick resetting `next_action_at` and firing ask 2 minutes after ask 1.
- **`lead_is_suppressed` is the single resolver for whether we may message a lead at all** — parked, handed-off, stopped, out-of-area, inactive, cancelled/completed, and job-already-booked. It is re-checked **before every customer-facing send**, not once at the top of the run: a lead can be parked or booked between two ticks.
- **`extract_expected_date` is deterministic and narrow on purpose.** A named day ("15/03", "20 October", "next Monday", "tomorrow") switches a lead from Case B to Case A via `record_lead_expected_date`; a rough answer ("in a few weeks", "sometime next month", "asap") must NOT match, or a confirmation goes out for a day nobody chose. `note_inbound_reply` is the hook, wired into `handle_text_message` and `process_inbound_emails`, and is a no-op for any lead without a live report.
- **`visit_end` does not trust `end_datetime` blindly.** `Appointment.save()` fills it once and never recomputes it, so a rescheduled visit carries the end time of the slot it used to hold; taking it at face value emailed the plumber a debrief for a visit that had not happened yet. A stale end (earlier than the start) falls back to `scheduled_datetime + duration`.
- **No follow-up renders a null date.** `build_post_visit_confirmation_email` raises rather than print a blank, and a confirm-branch report that somehow has no date falls back to the ask sequence instead of sending. The ask copy carries no date at all. The visit has already happened by the time these go out, so **the copy never re-pitches it** — "free", "site visit" and "no cost" are absent by test, which is the repeat-pitch rule applied to a new channel.
- Pinned by `PostVisitFormTests`, `PostVisitSchedulerTests`, `PostVisitDateParsingTests`, `PostVisitCopyTests` and `QuoteSendChannelTests` in `bot/test_views_actions.py`, plus the deterministic date/guard/cadence cases in TEST 0.

### Email
- **Inbound: the bot answers email too** (`process_inbound_emails`, 5-min cron), but **EMAIL IS REPLY-ONLY: it answers only people already in the system with a WhatsApp record, and no email ever creates a lead** (2026-08-24 rule; cold-email intake and its `INBOUND_LEAD_ADDRESSES` address->tenant routing were removed). A reply on a thread we started is matched by the `<apt-{id}.…>` Message-ID (or a legacy `[APT-{id}]` subject tag); an email with no thread reference is matched to a lead by `customer_email` (`_known_lead_for_sender`, most recently updated wins, subject folded into the customer's turn since off-thread the subject often IS the request). Either way the matched lead must pass `_is_whatsapp_lead` — a real phone number, not a synthetic `email_…` (legacy cold-email row) or `quotation_only_…` key — so the check is about the LEAD, not about how the mail matched. Everything else (receipts, support tickets, strangers writing in cold) belongs to nobody in the CRM and is left UNREAD for a human. No routing is needed for multi-tenancy: the matched lead carries its own tenant. **Two gates sit in front of the rule** (the polled inbox is the operator's personal Gmail, so the bot once opened leads on Stripe receipts and replied to them): (1) `_is_our_own_mail` drops our own traffic BEFORE the thread tag is trusted — the polled address, `DEFAULT_FROM_EMAIL`, every tenant `customer_from_email`/`email_sender`, `PLATFORM_NOTIFICATION_EMAIL`, `PLUMBER_NOTIFICATION_EMAILS`, the owner accounts, and anything on `PLATFORM_EMAIL_DOMAIN`; the Bcc copy of our own customer email carries the same `[APT-{id}]` reference the customer's reply does, so an APT match alone is not proof a customer wrote. (2) `_is_automated` drops machine mail (Auto-Submitted / List-Id / X-Autoreply headers, no-reply & mailer-daemon & receipt/billing/stripe addresses, bounce/out-of-office/receipt subjects) — without that guard the bot email-loops. Mail the bot declines is left **UNREAD** and its body is never downloaded: fetches use `BODY.PEEK` (`_fetch_unseen_headers` → gates → `_fetch_message`), because a plain `RFC822` fetch silently marks the operator's own mail read. Any new mailbox-touching code must keep the peek-then-gate order. A `--dry-run` neither replies nor marks anything seen.
- Email-only leads have no phone number, so they are excluded from proactive WhatsApp: `send_followups` skips `email_`/`quotation_only_` prefixes and `send_reminders._send_wa` refuses any non-numeric recipient. Any new synthetic-key lead type must do the same.
- **Two sending identities per tenant** (`bot/plumber_notifications.py`): `tenant_platform_from_email` → `<tenant-slug>@notifications.homexmedia.com` (`PLATFORM_EMAIL_DOMAIN`) is used for **internal** alerts — the mail to the operator and to the tenant's own inbox; `tenant_customer_from_email` → the tenant's own domain address (`TenantProfile.customer_from_email`, set on the Profile page) is used for **everything the tenant's clients receive**, falling back to that platform sender when unset, and to `DEFAULT_FROM_EMAIL` only for tenant-less platform mail (password resets). Resolution happens once at the `send_email_to_recipients` choke point and is threaded to all three transports as `from_email`/`reply_to`; only `send_plumber_notification_email` passes an explicit `from_email`. Reply-To follows From on any tenant-scoped send, so a customer's reply reaches the tenant, never the platform inbox. **One shared authenticated domain with a per-tenant local part — deliberately not a subdomain per tenant: every distinct domain needs its own SPF/DKIM records and consumes one of Brevo's authenticated-domain slots (the account is on the free tier). DNS: `notifications.homexmedia.com`, and any tenant domain, must be SPF/DKIM-authenticated in Brevo before it delivers.** Note `email_sender` is a recipient inbox, `customer_from_email` a sending identity — never conflate them.
- Customer/transactional email goes through the **SendGrid v3 HTTP API (port 443)** in `bot/plumber_notifications.py` (`_send_via_sendgrid`); Railway blocks all outbound SMTP, so the legacy `IPv4SMTPBackend` (`bot/email_backends.py`) is a fallback only. SendGrid click/open tracking is disabled to keep `tel:`/`wa.me` links clean. HTML lives in `bot/customer_emails.py`; subjects carry `[APT-{id}]` so IMAP replies match back to the appointment.

Static checks can't see this; run the rendered page in jsdom.

### The outbound chain, and the one step that skipped it
- **`finalise_outbound(reply, appointment, message_body)` is every rewrite a reply gets between composition and the wire**: the memory check, the fee stripper, the repeat-free-visit stripper, the visit-price note and the dash stripper, in that order. It exists because **STEP 0 (multi-intent compose) sent its own reply straight to `delayed_response` and skipped all of it** — so a fee tenant's multi-intent answer could have promised a free visit with nothing to correct it, and no reply from that path was ever de-dashed. Any new send path calls this rather than repeating the chain.
- **STEP 0 recorded the priced intents it sent but never checked them.** The single-intent branch has always called `_has_sent_pricing_for_intent`; this one only called `_mark_pricing_intent_sent`. A lead who repeated themselves got the identical price block again (prod, Barmak lead 974, 2026-09-03 13:17 and 13:24, both logged 🧩 Multi-intent compose). It now drops through to the normal flow when every intent it would answer is a price already sent, while a genuinely new question in the mix is still answered.
- **`compose_multi_answer` is English-only** — every snippet, the combined-pricing line and the closer. A Shona lead got an English wall of prices where the single-intent path answers in Shona, so a Shona message now returns None and goes to that path: one answer in their own language beats two in the wrong one. **The scripted first-pass question bank (`_get_first_pass_question`, 13 branches) is English-only too and is NOT yet fixed** — that is why a Shona lead is asked "What area are you in?" in English.

### Conventions to follow
- Reuse existing infra; no new dependencies without being asked. Preserve WAMID dedup and exit-signal-first ordering.
- **Keep the quote out of the rule engine** — thread it as `quoted_context` to classification/LLM calls only; any new outbound send path must stamp its WAMID (`attach_message_id` / `record_sent_media`) or quotes to it break silently.
- **No Homebase value may reach another tenant's customer.** Every figure, number, name and place in customer-facing copy or an LLM prompt resolves through the lead's own tenant: prices via `TenantConfig` (`catalogue_price_lines`, `price_components`, `freestanding_tub`, `cheapest_labour_rate`), the plumber's line via `Appointment.plumber_contact()` (webhook alerts go through `_plumber_wa_number`; `send_reminders` groups briefings per tenant via `_tenant_plumber` and gives customers `_lead_plumber_contact`), the name via `business_name_for()` / `plumber_display_name()`, the place via `location_short()` / `location_city`. **Absent means omit, never borrow** — a tenant with no tub price gets the free-visit deflection, one with no plumber number gets the email alert only. The `PLUMBER_PHONE_NUMBER` / `PLUMBER_NAME` env vars are homebase's legacy fallback and must not be used for a lead that has a tenant. Fixed 2026-08-21: catalogue price sheet, tub pricing, both plumber-alert paths, the unified + service-type classifier prompts, and the "based in Harare" / "as little as US$20" / "the plumber's name is Takudzwa" copy were all still hardcoded.
- **Hours are the tenant's own week, plus an optional 24/7 emergency tick.** `business_hours['emergency_24h']` (a key on the same JSON — no column) is set from the Profile editor and the intake wizard; `TenantConfig.emergency_24h()` / `emergency_sentence()` / `emergency_tag()` are the only readers, and every hours-copy site (`_working_hours_line`, `_hours_clause`, `_open_hours_clause`, `_quick_hours`, `_grounding_facts`, `_hours_clock`, `_emergency_fact`, the hours FAQ fact, the email prompt) goes through them. Out-of-hours refusals end with the emergency offer instead of dead-ending the lead (`_emergency_offer` in both `models.Appointment` and `availability_mixin`). It does NOT widen the booking window — regular slots stay inside the tenant's day. Absent means omit: never promise 24/7 for a tenant without the tick.
- Prefer deterministic resolvers over LLM round-trips for short/fuzzy strings (see the quote intent fix); reserve the LLM for genuinely ambiguous language.
- **The free visit is said ONCE, at the start.** "free site visit" / "free assessment" / "free of charge" was asserted in ~77 copy sites and landed in almost every reply, follow-up and reminder; said once it is the USP that earns the appointment, said six times it reads as pleading and drags a lead who has already accepted the visit back onto cost. `strip_repeat_free_visit(reply, appointment, message)` de-qualifies it at the SAME outbound choke point as `strip_free_visit_claims` (so it catches the LLM paths, not just the hardcoded copy): the first reply that pitches the visit goes out untouched, every later one loses the claim. **The pitch survives — only the price claim comes off**, so "a free on-site visit" becomes "an on-site visit" (article fixed) rather than the sentence being dropped, which is the opposite of the fee stripper's rule and deliberately so: there a false promise is the worst outcome, here a deleted pitch is. Shapes handled: adjective, leading clause ("The visit is free — our plumber will…" → the rest is promoted), trailing clause, adverbial ("free on/when/at…"), a label parenthetical ("(Free site visit)"), Shona `mahara`, and a guard that never leaves a sentence hanging on its verb. `asks_visit_cost` is the override — a lead who asks what the visit costs gets the straight answer however often they ask (customer's own words beat the gate), and it reads the FAQ's own `free_quote` triggers via `faq.visit_cost_triggers()` so the two can't drift. `_visit_fact_line` drops "is free" from the LLM grounding fact once it's been said, so the model isn't fighting the stripper. The cron commands call the same resolver through `dequalify_free_visit(lead, message)` — applied where the message is composed, so `--dry-run` previews what actually goes out. `freestanding` / `free-standing` is guarded everywhere: it is not a price claim.
- **A tenant who CHARGES for the visit follows the same once-only rule.** `strip_free_visit_claims` used to append `visit_cost_sentence()` to every reply that mentioned the visit at all, so a fee tenant's lead read "The call-out to quote is US$20." on all five turns, including after they had booked — the same complaint as the repeated "free", with a harder number. It now states the fee on the first visit-related reply and after that only when `asks_visit_cost(message)` says they asked (the choke point threads `message_body` in; the param is optional so other callers are untouched). `_visit_fee_already_stated` matches the fee SENTENCE, never the bare figure — "US$20" is also a fixture price, and a false "already told them" would mean the fee never got stated at all. **The safety guarantee is unchanged and does not depend on this:** the free claim is still dropped from every reply, so a fee tenant can never be made to look free whether or not the figure is repeated. Inert today — `consultation_fee` defaults to None and no tenant sets one.
- **The visit price is stated ONCE, with the AVAILABILITY ASK, and it carries its own close.** Not the opener: a fee quoted before the lead knows what they are buying prices the job, while the same sentence at the moment we ask for a day answers the question they are about to ask anyway. The approved wording is "[Great, ]we can come for a quick site visit. There's a US$X call-out fee which covers the visit and we'll do a full check for you.[ NEWLINE If you decide to go ahead with the <service type>, we'll take that cost off the final price.] Want me to book you a time?" — **plain words on purpose** ("full diagnosis" is trade language) with the waiver as its OWN sentence, so it reads as an offer rather than a caveat hanging off the fee (`TenantConfig.visit_price_note(is_shona, opening, job_noun)`; `opening` adds the warm-up word only when the note leads the message, `job_noun` is the lead's OWN service type via `_visit_job_noun`, read back from `PROJECT_TYPE_CHOICES` the way it was offered to them, so the waiver names the thing they actually asked for: "the geyser repair", "the bathroom renovation". It degrades to "repair" then "work" while the type is unset or 'other', which is the only honest thing to say before they have told us; Shona keeps the two plain nouns rather than bending English trade labels. Note underscores are word characters, so the repair test normalises them or "geyser_repair" never matches `repair`). **It is its own turn, after the area answer and before the availability question.** `strip_free_visit_claims` no longer volunteers the figure at all: it used to speak whenever a dropped free claim would leave a hole, which fired on the AREA question (the Shona quote pitch says "mahara", the claim is dropped for a fee tenant, and "The call-out to quote is US$10" was stapled onto "What area are you in?" — prod, Barmak, 2026-09-03 18:57). Worse, having been stated there, the note then saw the price already stated and never fired, so the lead met the figure at the worst possible moment and never got the offer that makes sense of it. It now speaks ONLY when the lead asks; dropping the false promise stays unconditional, so safety never depended on saying it. `asks_visit_availability` is the deterministic trigger and **the note REPLACES that question** (`_question_offset` finds it) rather than sitting in front of it: two questions in one reply breaks the house rule and the lead answers only the last one anyway. Whatever the reply said BEFORE the question is kept. Runs LAST at the choke point.
- **The lock-in close is a yes/no, so BOTH answers are handled.** `_handle_no_to_lock_in` (routed in the webhook beside the other no-handlers, before the slot-offer one) answers a refusal without ever re-sending the close or restating the figure. The no is ambiguous in a way a day/time no never is, because the message it refuses just named a fee: it can mean "not at that price" or "not right now". So it ISOLATES rather than guesses, in one question with two options, and **the fee only appears as an option for a tenant who charges one** — offering "or is it the call-out fee?" to a lead told the call-out is free invents an objection they never had. `_declines_lock_in` is deliberately wider than `_is_bare_negative` ("no thanks", "not yet", "maybe later" are how people decline a yes/no close) but capped at five words, so "no thanks, I got someone to do it Friday" keeps its information. A HIGH delay signal ("not right now") is handed BACK to the delay flow, which parks the lead with a real check-back date instead.
- **The customer's own words override any gate or holding state.** Every gate that auto-replies (price) or parks the lead in a flow must let a real signal in the *current* message — a named product, an explicit price ask, an elliptical "this one?" on a quoted photo, an exit/delay signal — win over a carried-over LLM intent or a pending flow state. This one bug recurred four times in four code paths (tub misclassification; area reply → unprompted price ×2; price question swallowed by the delay-timeframe wait). The shared deterministic resolvers are `_correct_service_intent`, `_is_unprompted_carryover_pricing` (+ `ResponseMixin._is_carryover_pricing`), `_is_quoted_item_reference`, `_delay_breakout_inquiry`, `_should_volunteer_pricing`, `_is_purchase_commitment`, `_is_job_quote_request` / `_names_multiple_products` (+ `_build_combined_price_reply`, `_build_job_quote_reply`), and `wants_whatsapp_delivery`. **Any change to intent classification, the pricing gates, or flow routing MUST add/extend an API-free case in `tests/test_bot_responses.py` TEST 0** — now enforced by the pre-commit gate (see "Tests & the commit gate").
- New per-turn metadata = optional JSON keys, never new columns; new handler params stay optional with `None` defaults so existing callers keep working untouched.
- **No emojis in customer-facing copy** (logs/dashboards fine). Support English + Shona.
- **No dash PUNCTUATION in customer-facing copy.** Nobody types an em dash on a phone, so a reply full of them reads as drafted prose rather than a text message. `utils.strip_dashes` turns a clause dash into the comma or full stop the sentence was reaching for (interrogatives and independent clauses start a new sentence, short interjections take a stop: "Perfect - thanks" becomes "Perfect. Thanks"), a range into "to" (`8am-6pm` -> `8am to 6pm`, `Sun-Fri` -> `Sun to Fri`), and a line-opening dash into a bullet. **Hyphens INSIDE words are left alone** (`on-site`, `all-in`, `wall-hung`, `call-out`, `20-minute`): stripping those would give "onsite" and "allin". Applied LAST at the outbound choke point, after the price note is appended, plus in `dequalify_free_visit` for cron copy and beside every existing `strip_emojis` call (the LLM output points). Every prompt that bans emojis now bans dashes too, so the model shapes the sentence for a comma instead of having one repaired afterwards. **Do NOT bulk-rewrite dashes in source**: an automated pass over the literals broke the hours formatter (`{a} - {b}` range templates) and the photo-description delimiter that `_describe_work_image` writes and the keyword resolver parses back. The stripper runs on the FINAL rendered message, which is the only layer where a dash is certain to be punctuation and not structure. ~75 high-traffic strings were hand-rewritten; the tail stays in source and is cleaned at output.
- **Windows-local gotcha:** handlers `print()` emoji; set `PYTHONIOENCODING=utf-8` or local shell/test runs raise `UnicodeEncodeError` (harmless on Railway's UTF-8 stdout).
