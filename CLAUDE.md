# Plumbot – Claude Code Instructions

## Project Overview
Plumbot is a WhatsApp-based appointment scheduling and sales chatbot for Homebase Plumbers in Harare, Zimbabwe. It is built with Django, deployed on Railway, uses Twilio for WhatsApp messaging, and DeepSeek API for AI-powered intent classification and response generation.

## Core Files
- `whatsapp_webhook.py` / `views.py` — main conversation flow logic
- `send_followups.py` — Railway cron job for follow-up scheduling
- DeepSeek API integration — intent classification and response generation

## Coding Rules
- Never introduce new dependencies unless explicitly asked
- Reuse existing infrastructure and patterns already in the codebase
- Always preserve WAMID deduplication logic — never remove it
- Exit-signal detection must always run before any flow-stage logic
- Never re-pitch the site visit to a customer who has already committed

## Conversation Flow Logic
Plumbot uses Hormozi's four-stage qualification framework:
1. **Value** — lead with what we offer and why it matters
2. **Price** — be upfront about pricing before heavy qualification
3. **Qualification** — ask targeted questions using "this or that" framing
4. **Close** — use presumptive closes and micro-yes ladders

When editing flow logic:
- Customers may respond with partial answers (e.g. just a day name like "Sunday") — always handle fuzzy/partial date-time inputs gracefully
- Support both English and Shona responses
- Avoid bot loops — if a question has already been asked, do not repeat it
- Use the semantic duplicate question detector before sending any qualification question

## DeepSeek API Integration
The DeepSeek API is used for intent classification and response generation. When improving prompts or API calls:
- Embed step-by-step reasoning instructions in the system prompt
- Instruct the model to identify customer intent before selecting a response
- Use chain-of-thought style prompting: interpret → consider alternatives → select stage → respond
- Keep responses short, warm, and conversational — like a knowledgeable colleague texting

## System Prompt for DeepSeek
When generating or editing the DeepSeek system prompt, use this as the base:

---
You are Plumbot, a WhatsApp sales and scheduling assistant for Homebase Plumbers in Harare, Zimbabwe. Before every response, reason through the following steps internally:

1. **Intent** — What is the customer actually asking or signaling? Look beyond the literal words.
2. **Stage** — Which of the four stages are they in: value, price, qualification, or close?
3. **Ambiguity** — Is their message unclear or partial (e.g. just a day name, a one-word reply)? If so, clarify gently without repeating yourself.
4. **Commitment signals** — Are they showing readiness to book? If yes, move to close immediately.
5. **Exit signals** — Are they trying to leave the conversation? If yes, acknowledge gracefully and leave the door open.

Then respond:
- In the same language they used (English or Shona)
- Warmly and conversationally — never robotic
- Concisely — WhatsApp messages, not essays
- With presumptive framing — offer choices, not yes/no questions
- Leading with value and confidence, not desperation
---

## Common Bugs to Watch For
- Bot re-pitching site visit after customer already agreed → check commitment state before sending pitch
- Price queries falling through to wrong flow stage → classify price intent before stage routing
- Duplicate messages → always check WAMID before processing
- Follow-up cron skipping eligible leads → check lead eligibility filter logic carefully
- Flow not advancing on partial date inputs → normalise day names to full date-time before validation

## Current State

Orientation for the next session: what the system does today, why it's built this way, what's fragile, and the conventions to keep. Reflects the codebase as of June 2026.

### Stack & composition
- Django app `bot/` on Railway; WhatsApp via Twilio/Meta Cloud API; all AI via **DeepSeek** through the OpenAI SDK pointed at `api.deepseek.com`.
- The shared DeepSeek client (`bot/services/clients.py`) monkey-patches `chat.completions.create` to **force "thinking" mode off on every call** — thinking mode ate the `max_tokens` budget and returned empty/truncated JSON, breaking every classifier (`DEEPSEEK_THINKING=enabled` reverts).
- `Plumbot` (`bot/views/plumbot/`) is one class composed from mixins — `state`, `response`, `extraction`, `availability`, `booking`, `reschedule`, `notification`, `plan_upload`; `base.py` wires them and `get_or_create`s the `Appointment` per phone number.

### Inbound pipeline (`bot/whatsapp_webhook.py`)
- `process_message_change` → `handle_text_message(sender, text, message_id, quoted_id)` logs the user turn, resolves any quoted reply, then **debounce-batches per sender** (`_enqueue_for_response` / `_flush_text_batch`) so rapid-fire texts get a single answer.
- `_generate_and_schedule_reply` is the router; the first step to produce a reply wins, in order: FAQ → unified pre-classifier → STEP 0 multi-intent compose → 0a whole-gallery → 0b specific portfolio piece → 0c portfolio menu → 0d catalogue+prices → 1 photo request → 1b out-of-scope/delay/complaint → 2 service-specific pricing → 2b quote-with-no-product (`_routes_to_onsite_quote`) → 3 full pricing overview → 3b repeated-question → 4 normal `generate_response`. **STEP 2b exists because the quote rule was gated on a priceable intent.** "A quote is delivered at the visit, never as a chat price block" was only ever asked inside STEP 2, so a quote for a WHOLE JOB — which names no product family and classifies as intent 'none' — fell through to STEP 3, where `detect_objection_type` reads the word "quote" as a pricing objection and `_is_genuine_pricing_question` lets the full overview fire: "May I get a quote for a four bedroomed house" came back as the Facebook package plus bathtub prices, a bathroom price list for a whole-house job (prod, barmak 2026-09-05). `_routes_to_onsite_quote` is the counterpart of `_is_genuine_pricing_question` and is asked FIRST — both trigger on the word "quote", only one is the business rule. A confirmed lead is excluded, so the visit is never re-pitched to someone who has booked.
- Outbound goes out on a **1–5 min random delay** via `delayed_response` in a daemon thread; a newer inbound message **cancels the pending send** (`_pending_send_events`) so the batch re-runs with the latest context.

### Unified classifier (`bot/unified_classifier.py`)
- One DeepSeek call returns a dict consumed by all downstream handlers (OOS intent, product/service intent, booking-data extraction, photo/repeat/plan-later flags), replacing ~6 separate calls; on failure it returns `None` and callers fall back to their own classifiers. Access via `uc_as_service_inquiry`, `uc_as_oos_classification`, `uc_is_photo_request`, etc.

### Conversation storage (`bot/models.py` — `Appointment`)
- `conversation_history` is a schemaless `JSONField` of `{role, content, timestamp}` dicts plus optional `message_id`/`quoted`/`media_index` keys — transcript metadata never gets a migration.
- **The transcript holds what was SENT, never the draft of it.** Two layers log an assistant turn: the response mixins log the reply the moment they compose it (~20 call sites, some on paths that never reach the webhook), and the webhook logs the final text at the outbound choke point. Between them sits the whole rewrite chain (memory check, fee + repeat-free-visit strippers, the first-message price note, dash stripping). `add_conversation_message` de-dupes on EXACT content, so while the chain changed nothing the two writes collapsed and nobody noticed; the price note edits the FIRST reply of every conversation, so they stopped matching and the dashboard showed each opener twice, once without the note and once with it, while the lead received only the second (prod 2026-09-03, barmak-plumbing 263786318169). `Appointment.replace_draft_assistant_turns(draft, final_parts)` now drops the draft run and logs the final text; `_generate_and_schedule_reply` captures `_draft_reply` before the chain and calls it instead of appending. A turn already carrying a WAMID was really sent and is never dropped. **Any new step added to that chain is safe automatically; any new outbound path that logs its own reply must go through this helper, not a bare append.**
- Helpers: `add_conversation_message` (logs a turn; back-fills WAMID/quote onto a duplicate entry), `attach_message_id` (stamps an outbound WAMID after the send returns), `record_sent_media` (one entry per image batch carrying `{wamid: description}`), `resolve_quoted_message` (maps an inbound `context.id` → stored text/image description).

### Quoted-reply ("highlighted message") feature
- WhatsApp delivers only the quoted message's **WAMID** (`context.id`), never its text, so outbound WAMIDs are stamped onto history (text in `delayed_response`, images in `send_previous_work_photos` via `record_sent_media`) and resolved locally on the way back.
- The resolved quote is a **separate** `quoted_context` value that reaches classification/LLM calls only — never the rule engine. Before STEP 2, `_generate_and_schedule_reply` re-derives the service intent **deterministically** with `_keyword_product_intent` (the customer's own product word wins, else the quoted caption — e.g. a "rain shower" quote → `shower_cubicle`), so "this one how much?" on a portfolio photo prices the quoted item, not a stale carried-over intent. Deterministic on purpose: the LLM mis-maps short captions (a "rain shower" caption came back `tub_sales`).
- Fragile: resolution coverage is **not universal** — only the two stamping send-paths resolve; messages sent via direct `send_text_message` (plumber alerts, photo intro line, `generate_photo_followup`) and pre-feature history return `None` and silently behave quote-less (signature log: `🔗 … not found in history`). And the quote only steers STEP 2 intent + `generate_response`; the availability/date classifier, FAQ, and booking path don't see it.

### Portfolio / catalogue (`bot/portfolio_catalog.py`)
- Static list of previous-work pieces (title, "from" price, description, keywords). `match_portfolio_item` returns a single item only when the message clearly references one piece, else `None` → whole-gallery send; `_describe_work_image` derives a per-image description (curated title for catalogued files, tidied filename otherwise) for the media index. Prices are the business's own "from" rates from `bot/sales_profiles/homebase.md` (source of truth — keep in sync, never invent figures); captions are title-only.

### Pricing & sales (`bot/views/plumbot/response_mixin.py`)
- `detect_service_inquiry` → priceable intent; `handle_service_inquiry(intent, message)` builds the reply from a `structured_pricing` table keyed by intent (the message is used only for language detection). `generate_pricing_overview` gives the full menu; `compose_multi_answer` answers 2+ info questions in one reply.
- Pricing is gated: don't volunteer price when unasked, don't re-send an already-sent intent, and don't price a message that's a project description / booking-capture answer.

### Booking, availability, scheduling
- `extraction_mixin` pulls fields (service, area, plan status, name, datetime) and tracks `get_next_question_to_ask`; `availability_mixin` checks business-hours slots and suggests alternatives; `booking_mixin` validates completeness and books; `reschedule_mixin` handles AI-detected reschedules; `plan_upload_mixin` runs "I'll send my plan" flows and plan-status nudges; `notification_mixin` alerts the plumber and optionally Google Calendar.
- **`_job_is_known()` is THE single answer to "do we know enough about the job to book it?"**, read by BOTH `get_next_question_to_ask` (extraction_mixin) and `smart_booking_check` (booking_mixin). They used to disagree: the question order has treated a captured description as answering the service question since 2026-07-02 (a lead who said "2x shower cubicles and accessories" must not be bounced back to the opener), while the booking check went on REQUIRING `project_type`. **A lead carrying only a description therefore had nothing left to be asked AND could never be booked** - unbookable by construction. That is where barmak lead 1144 died (2026-09-09): description and area captured off the opening message (`_build_job_quote_reply` stores a general quote request as the description), "Thursday afternoon, 3pm?" stored as the slot, `ready_to_book` False forever on the missing type. Status stayed `pending`, so there was **no confirmation, no plumber alert and no name ask**, and with the deterministic flow out of questions the turn fell through to the LLM. The DESCRIPTION wins the tie because it is the customer's own account of the job, and everything downstream degrades honestly without a type (`_visit_job_noun` -> "work", `_describe_project_context` -> "the space"). Pinned by the `booking:` cases in TEST 0 and `DescriptionOnlyLeadBooksTests`. **Still open:** that stored description is the lead's REQUEST ("I'd like a quote for some plumbing work"), not an account of the job, and because any non-empty string satisfies `controller.description_captured` the bot never asks what the work actually is.
- **The customer's booking confirmation is queued, not sent inline.** `send_confirmation_message` builds plain conversational copy (`_build_confirmation_message` — no headings, no labelled fields, no emojis, mirroring the lead's language, absent details omitted rather than filled with "Your area") and hands it to `delayed_response` on a daemon thread after `CONFIRMATION_DELAY_MIN/MAX_SECONDS` (45-90s), so it lands like a person writing the details up rather than a receipt printed the moment the row saved — and so the turn is logged and its WAMID stamped. Duplicate sends are blocked by `_claim_confirmation_send`: one conditional UPDATE writes a `[CONFIRMATION_SENT:<slot>]` marker into `internal_notes`, so a repeated "yes" or a second press of the dashboard Confirm button claims nothing, while a genuine reschedule to a new slot still confirms.

### Rescheduling (`reschedule_mixin`)
- Routed from STEP 4 of `generate_response` on a confirmed lead. `detect_reschedule_request_with_ai` (DeepSeek) decides, falling back to the deterministic `detect_reschedule_request` keyword list (English + Shona) when the API is down; `parse_datetime_with_ai` extracts the new slot, `_reschedule_availability` checks it, `process_successful_reschedule` moves it.
- **`_reschedule_slot()` is the single resolver for WHICH appointment moves.** `schedule_job_appointment` keeps ONE row — it flips `appointment_type` and fills `job_scheduled_datetime`, leaving the completed site visit in `scheduled_datetime` — so a confirmed lead can hold two datetimes. Every path (the STEP 4 gate, the detector's quoted time, the availability check, the write, the plumber alert, the email command) goes through it. Before that, a job customer's move was quoted against their old site visit and written to `scheduled_datetime`, while the jobs board and `send_job_reminders` went on reading `job_scheduled_datetime`. A job also checks availability against its own duration (`check_job_availability`), not a single slot.
- `process_successful_reschedule` writes the resolved field, notes the move on the lead with `_append_admin_note` (the old `reschedule_count` / `original_datetime` assignments were guarded by `hasattr` for columns that don't exist, so nothing was ever recorded), then fires the calendar move and `notify_team_about_reschedule`, each best-effort in its own try. **If the save itself fails it returns `_reschedule_breakdown_reply()` — never tell a customer their appointment moved when it didn't.**
- **Three of the methods this flow called never existed** — `notify_team_about_reschedule`, `update_google_calendar_appointment`, `detect_reschedule_request` — and each `AttributeError` was swallowed by the caller's `except`: the plumber was never told, the calendar kept the old slot, and an API blip crashed detection instead of degrading. `add_to_google_calendar` now stores `google_calendar_event_id` so `update_google_calendar_appointment` can PATCH the event (it creates one when no id is on file). A TEST 0 case asserts every method the flow calls is defined — keep phantom calls out.
- Reschedule copy is deterministic (`_build_reschedule_confirmation` / `_build_reschedule_clarification` / `_build_reschedule_unavailable_reply` / `_reschedule_breakdown_reply`): no emojis, mirrors the lead's language, hours via `_hours_clause` (the old fallback hardcoded "8 AM - 6 PM, Monday to Friday" for every tenant), and the breakdown reply offers the tenant's own `plumber_contact()` or no number at all — it used to send every customer to the placeholder "(555) PLUMBING".
- Emailed reschedules go through the same pipeline via `_apply_email_reschedule` in `process_inbound_emails` (availability first; a taken slot moves nothing and asks for another day), so an email move alerts the plumber and updates the calendar exactly like a WhatsApp one.

### Follow-ups & cron (`bot/management/commands/`)
- `send_followups` — **FOUR is a CEILING, and FOUR HOURS is a FLOOR** (owner rule, 2026-09-09, superseding "four for every lead" of 2026-09-03 where the two collide). Three rules, in one place each: (1) at most `FOLLOWUP_CAP_PER_REPLY` = 4 touches between one message of the lead's and the next, counted by `touches_since_last_reply` off the TRANSCRIPT rather than any one loop's counter (each loop keeps its own — `followup_count`, and the two nudge states in `internal_notes` — and none can see the others, so a lead chased four times and then parked could be nudged four more times off the same silence; a `[MANUAL FOLLOW-UP]` by a human is deliberately not counted, since the cap is about the machine talking over itself). It is asked FIRST in `_is_ready_for_followup` and again in both nudge loops. (2) `FOLLOWUP_MIN_GAP_HOURS` = 4.0, and `LAST_CALL_MIN_GAP_HOURS` now EQUALS it — the old 0.75h last-call relaxation is gone, because a minimum is a minimum. `space_offsets` is the single spacing resolver, shared by the main schedule and both nudge loops: it pushes a close pair apart and **DROPS what no longer fits rather than squeezing it**, so when the gap and the count cannot both hold, the COUNT gives. (3) Every touch is contextual — see the fallback templates below. **THE MEASURED CONSEQUENCE: an ad (72h) lead still gets its four, but a standard 24h lead now gets 1 to 3, usually 2.** That is arithmetic, not a bug: `CONTACT_WINDOWS` allows ~5.5 sendable hours a day in two blocks, so a 4h floor permits at most two sends per day, and a 24h window overlaps at most one day of contact hours. The knob is `CONTACT_WINDOWS` — a wider sendable day is what would buy a 24h lead four touches again. The count is read off the schedule everywhere (`max_followups_for` = `len(followup_offsets_for(lead))`), so the UI chip, the dashboard due-list, the LLM prompt and cron retirement all follow it without being told.
- **The offline fallback templates are contextual too** (`_template_message`). Every touch names the lead and names their job in their OWN words via `lead_handoff.job_phrase` — the same resolver the plumber's draft reads, so a lead is never "a bathroom renovation" in one message and "your project" in the next — and the shortest, fourth attempt still names it: "Still looking for a plumber?" was the last thing some leads ever heard from us. Two things were removed on the way: **fabricated scarcity** ("we're getting booked up this week", "we're getting tight on slots this week" appeared in four banks and were true of nothing — the cron has no idea what the diary holds, the sales rules forbid invented urgency, and a line identical for every lead on earth is the opposite of contextual), and **tenant claims** ("we price the job upfront", "the price is fixed once we confirm", "locking in a slot costs nothing" are one business's USPs and one business's visit policy). Pinned by the `followup rules` / `followup cap` / `followup context` cases in TEST 0.
- Placement, unchanged except where the floor now truncates it. On a full 72h window the touches take the band placement: **2 in the first 24h, 1 in 24-48h, 1 in 48-72h**, measured from the lead's last message — `FOLLOWUP_BAND_OFFSETS` as absolute hours per temperature (COLD 6/13/33/60h, VERY_HOT 4/10/27/51h), with `FOLLOWUP_BANDS` the contract in data and TEST 0 asserting every tuple against it. **Temperature moves a touch WITHIN its band, never into another one.** **Only a 72h window can carry that placement** — a touch written for 33h could only ever bounce with 131047 on a window that shut at 24h — so any shorter window (a standard lead, or an ad lead who replied with most of the 72h spent) gets `SHORT_WINDOW_FRACTIONS` instead: the same four touches as a share of the usable span (24h COLD ≈ 3.6/8.6/13.5/18.9h, 48h left ≈ 7.4/17.7/27.9/39.1h). Fractions rather than a second hour table, so one branch covers every window length. `followup_offsets_for(lead)` is the resolver and picks the branch on `bands[-1] <= usable_window_hours`; **the count is read off it** — `max_followups_for` is `len(followup_offsets_for(lead))`, so cron retirement, the UI chip, the dashboard due-list and the LLM prompt cannot disagree with the schedule, and `FOLLOWUP_MIN_COUNT` = 4 is the written run length, which `space_offsets` may now truncate; the nudge loops read their own `len(offsets)` rather than "at least four". Absolute offsets mean a touch deferred by the nightly contact window cannot push the later ones past the close — the old cumulative cadence (COLD 4+6+6+6 = 22h + jitter) overshot the 24h window and silently retired leads on three. **A reply resets the counter to zero** (`Appointment.reset_followup_sequence`, called from `mark_customer_response` and from the emailed-reply stamp in `process_inbound_emails`): the run is four touches SINCE THEY LAST SPOKE, so a lead who answers is never retired, and a reply revives one the cron already retired since it reopens the window too. It sets fields only — the caller saves. `last_followup_sent` is deliberately NOT cleared: it is the durable "have we ever chased this lead" record (the webhook's `mid_conversation` check reads it, since the counter no longer survives a reply). **Ad leads no longer get a bigger COUNT** — the old six-touch `CTWA_FOLLOWUP_OFFSETS` / `has_extended_window` path is gone; the longer window buys spacing, not extra messages. **Placement is reconciled with SENDABLE hours** — the messaging window intersected with `CONTACT_WINDOWS` (12:33–14:33 and 16:02–19:33, two windows, every day, half-open so the last send in each is 14:32 and 19:32, SAST — owner rule, 2026-09-06, widening the 2026-09-05 bounds; the TEST 0 window cases derive from `CONTACT_WINDOWS` rather than retyping it, and `plan_quote.in_contact_window` reads the same constant, so the owner moves these hours in ONE place): the sendable span no longer shortens the SCHEDULE (`_sendable_hours` and `MIN_SENDABLE_SPAN_HOURS` are gone — shrinking the span dropped a whole touch where moving it would do), instead `_scheduled_due_at` rolls a due moment forward out of the quiet hours and, when that roll would land after the window has shut, pulls it BACK to `_last_sendable_moment` minus `LAST_CALL_GRACE_MINUTES` (`_window_moment_before` is the mirror of `_next_window_open`). Without that pull-back a touch due at 02:00 on a window closing at 06:00 waited for 08:21, by which time free-form sending was dead — so it only reached the lead when they messaged again, arriving as a stale nudge on top of their live message. A last call no longer relaxes the spacing (`LAST_CALL_MIN_GAP_HOURS` == the floor): what gives in that stretch is the TOUCH, dropped rather than squeezed. Two guards keep a touch off a live exchange: `FOLLOWUP_LIVE_CONVERSATION_MINUTES` (the lead just wrote — the bot's own reply is the touch; this also replaces the old 2-minute eligibility prefilter) and `FOLLOWUP_QUIET_AFTER_OUTBOUND_HOURS` (we just wrote). The delay-ghost and parked nudge loops share the last-call rule via `_is_last_call`. Delay-flow and parked nudges use the same rule (`_DELAY_NUDGE_FRACTIONS`, `_PARKED_NUDGE_FRACTIONS`), go through the same `space_offsets`, and are capped by the same cross-loop ceiling — parked nudges moved from 3/7 DAYS (always outside the window, so every one bounced 131047) into the back half of the window. A closed window still blocks everything: we never pay for templates. Other Railway crons: `send_reminders`, `send_job_reminders`, `summarize_unconfirmed_leads`, `process_inbound_emails`, `send_scheduled_followups`. **Every service in the Railway project shares the repo's `railway.json`, whose `deploy.startCommand` overrides each service's own** — so all of them boot `start.sh`, which runs `manage.py <job>` when `PLUMBOT_CRON` is set (comma-separated for a service carrying several jobs) and gunicorn when it isn't. Adding a cron = new service + `cronSchedule` + a `PLUMBOT_CRON` value, never a start command in the dashboard (it would be overridden). The `_cronsReference` block in `railway.json` documents the current mapping (services: `Follow_Ups`, `Reminders`, `Email_Follow_Ups`, and the `Plumbot_v1` web role); Railway does not read it. **A Railway deployment bakes in the cron schedule the service had when that deployment was created.** One built while the schedule was absent comes out `buildOnly=false` / `cronSchedule=null`: it runs `start.sh` once at deploy time and never ticks again, while the service page still shows the schedule and Railway keeps advancing `nextCronRunAt` — silent, with the deployment sitting at SUCCESS. That stopped `send_followups` dead from 2026-08-25 to 2026-08-28; the only follow-ups sent in between came from a human pressing the dashboard's manual follow-up check (`manual_followup_check`), which runs the command inside the WEB service. `railway redeploy` does not fix it — it replays the bad snapshot; re-apply the schedule (`serviceInstanceUpdate`) then deploy fresh (`serviceInstanceDeployV2`). To check a cron service is genuinely alive, read its latest deployment meta (`buildOnly` true, `serviceManifest.deploy.cronSchedule` set) and confirm its `deploymentLogs` carry one `[start.sh] cron job` line per tick — the DB alone cannot tell a dead cron from a quiet one. See `_cronScheduleTrap` in `railway.json`. (`notify_priority_leads` — the daily plumber WhatsApp alert — was removed 2026-07-08; the priority-leads dashboard pages remain.)

### Post-visit debrief + quote follow-ups (`bot/post_visit.py`)
- Everything after a site visit hangs off **one row, `SiteVisitReport`** (OneToOne on the lead, migration 0077), and **one tokenized URL**. Two entry points open that same URL: the **in-app banner pinned at the very top of the appointment detail screen** ("Is the site visit complete?" → `site_visit_start`, staff-only, creates the row then redirects). **It replaced the old `complete_site_visit` view, URL and template, which are deleted** — that button sat buried in the Scheduling card and wrote `site_visit_notes` / `plumber_assessment` with no quote and no follow-ups behind it. There is now ONE way to log a visit. The banner is **always rendered and never gated on the row looking tidy** (not on `status='confirmed'`, not on a past slot): plenty of real visits happen without the bot ever pinning a slot, and gating the only control on that made those impossible to log. `_site_visit_banner` returns `{'state': 'open'}` or `{'state': 'resolved', 'report': ...}` — once logged it reports the outcome and what it set running rather than vanishing, so it is never a dead control. `is_due_for_report` still gates the CRON (an unscheduled lead has no visit-end to measure 35 minutes from); only the UI is ungated and the **fallback email to the plumber 35 minutes after the visit ends** (`send_site_visit_form_email`). One URL and one `submitted_at` is what makes the form single-use ACROSS both paths: `apply_submission` is the only writer of that timestamp and refuses a second call, and the cron stops sending the fallback the moment it is set. The form is deliberately **public, token-only** (`/site-visit/<token>/`, added to `TenantMiddleware._EXEMPT_PREFIXES`) — the plumber taps it from an email on their phone with no session; the token is a uuid4 and the row is single-use, so the link is the credential. Anything needing real authority (creating the quote) redirects to a staff-gated screen.
- **The banner lives INSIDE the Details tab and is NOT pinned** (owner rule, 2026-09-14, superseding the 2026-09-09 "above the tabs" arrangement). It sat above the tab bar so it was reachable whichever tab you were reading, but a banner about the SITE VISIT then held the top of the Quotes, WhatsApp and Email tabs, over content it has nothing to do with - and being outside the only scrolling box on the screen, it never moved off them. It is now the first child of `#tab-details`, which scrolls its own content, so it is still the first thing seen (Details is the tab a record opens on) and it scrolls away like anything else on a page. **The whole `is-flow-scroll` mechanism is gone** - the pane-level scroller, the id-spelled overrides, the sticky `.appt-tabbar` and the `showAppointmentTab` class toggle - because it existed only to unpin a banner that no longer sits there; each pane scrolls itself again and the tab bar stays visible by sitting above them. Do not reintroduce a pane-level scroller to make the banner "reachable from every tab": that is the arrangement this replaced. ### The reasoning controller (`bot/controller.py`, `bot/controller_templates.py`, `bot/visit_slots.py`)
- The model picks the MOVE; deterministic code writes anything the customer must be able to trust. `unified_classify` became **`unified_turn`** (old name kept as an alias) and now returns `reasoning`, `next_move`, `move_confidence` and `state_update.want_level` alongside the classification, on the same call — no extra round-trip.
- **The planning number is `move_confidence`, NOT `confidence`.** That key already means the classification's HIGH/LOW and is read by gates all over the bot; one key with two meanings would have a 0.8 silently answering "is this classification reliable?".
- **Planning failure never degrades classification.** A malformed plan returns the classification with the planning keys stripped. A plan that is entirely ABSENT gets no retry (`planning_attempted`): a missing plan means the prompt is not landing, and retrying every turn would double the call count on the busiest path while fixing nothing. A plan that is present but wrong is a one-off slip and gets exactly one retry.
- **Three gates enforce in code what the prompt only asks for.** `apply_fee_gate` holds `book_visit` back below `want_level='wants_it'`. `apply_plan_path_gate` suppresses it outright once we hold the lead's plan — it reads `plan_status`, never `has_plan`, because `has_plan` goes true when a lead SAYS a plan is coming and a promised plan is nothing to quote from. `work_already_shown` reads `previous_work_photos_sent_at`, never the model's `state_update.work_shown`: the model reports what it believes, the timestamp reports what happened, and when they disagree the gallery goes twice or never.
- `project_next_move` is the deterministic re-projection of signals the classifier already returns. It is both the fallback when the model omits a plan and the BASELINE shadow mode scores the model against. `present_value` projects off a whole-job `quote_request`, **never off a plain `price_ask`** — the visit fee is the only price we volunteer, but a lead who ASKS what a fixture costs still gets the from-price (owner rule, 2026-09-05).
- **Phase 0 (shadow) is live and drives nothing.** Two greppable log lines per turn: `[SHADOW-PLAN]` (what the controller proposed vs what the table projected) and `[SHADOW-BRANCH]` (which branch actually ran, whether they agreed, and `calls=` — the per-turn DeepSeek count, from `services/clients.start_turn_count`). **Phase 2 routing is ON** (`PLUMBOT_CONTROLLER_ROUTING`, default 1, set it to `0` to put everything back on the deterministic order without a deploy; a TEST 0 case asserts the default stays ON, and this paragraph said the opposite for a while after the promotion - read `controller.py` rather than this line if they ever disagree again). `DRIVABLE_MOVES` is `book_visit`, `handle_objection`, `show_work` and `close_pleasantry`; everything else stays with the old router, and all of it goes through `finalise_outbound` like every other send. **Two gates enforce 'the customer's own words outrank the model' for the two moves that would otherwise talk over them**: `close_pleasantry` is held back when `_asks_us_something` or `_booking_half_made`, and `show_work` when `_asks_us_something` **unless the question was a photo request** - "can I see your work?" is the one question whose answer is the work. Barmak 1144 asked "How do l book for a site visit" and got the gallery back, which answers a question they never asked and leaves theirs unanswered.
- `visit_slots` picks the days, never the model: always tomorrow and the day after, rolled past days the tenant is shut, Shona days for a Shona lead, and "the day after" only when "tomorrow" was actually said first (on a Friday with Saturday closed the first slot is Sunday, and "the day after or Monday" asks the lead to work out the day after what). `proposed_visit_date` is the future-dated equivalent.

### Two product paths to a quote (`bot/plan_detection.py`, `bot/plan_quote.py`, `bot/visit_proposal.py`)
- **MEASURE path** (no plan): sell the paid site visit. **PLAN path** (a real plan arrives): the drawing carries the measurements, so there is nothing to measure up and the plumber quotes off it. `classify_media_kind` routes on the description vision already produced plus the MIME type — no extra call. Its middle case is the one that was missing: `_description_is_a_plan` rejects a lone "drawing" or "layout" because both describe photographs, and those used to fall through as photos with nobody asking; they now get one clarifier. A room description still beats a stray layout word. No `media_kind` column — `has_plan`/`plan_status` already carry it.
- **`PlanQuoteRequest`** (migration 0081, command `send_plan_quote_followups`): the plumber is emailed the job plus the plan an hour after it arrives, or as soon as description/area/timeline are in, whichever is first; chased at +2h/+4h/+8h until they answer the tokenized single-use form; then the lead is asked about the quote an hour after the plumber confirms (Branch A) or at +12h assuming it went out (Branch B, `quote_status='assumed'`). **Branch B waits for a contact window, Branch A does not** — B fires on a clock and +12h from a 3pm plan is 3am, while A is triggered by the plumber tapping the form, which is itself proof of working hours.
- **`VisitProposal`** (migration 0082, command `send_visit_checkins`): a future-dated MEASURE lead is penciled in for a real day near their target, then asked to confirm by email at target −7 and −4 days with a yes and a no link. **A lead with no email is handed to the PLUMBER** — those two check-ins go to them instead (mornings only), carrying a `wa.me` link with a message written ready to send, which starts a fresh 24h window we cannot open ourselves.
- **The tentative state is its own row, NOT a new `Appointment.status` value.** Every dashboard filter, the diary query and the follow-up eligibility read that field, and a fifth value would change what each of them counts. `apply_lead_answer` is the only place a future-dated visit becomes real, and it **writes the diary FIRST, then marks the row**: the other order leaves the row reading 'confirmed' with nothing booked and the check-ins stopped, while the lead is told it failed.
- All three flows follow `post_visit.py`: anchors and offsets rather than a job queue (there is no scheduler in this codebase), every send gated by the timestamp written as it goes out, lead state re-checked before EVERY send, and one bad lead never stopping the run. `plan_quote.lead_is_done` extends `lead_is_suppressed` rather than replacing it — a `status='confirmed'` lead with a slot ahead is the ordinary state after a site visit but means "they booked, stop" on the plan path.
- **The plumber is contacted by EMAIL, always** (owner rule, 2026-09-05). The media alert, plan alert, booking alert, job alert and scheduled reminders all email; the three WhatsApp briefings in `send_reminders` are off behind `PLUMBER_WHATSAPP_BRIEFINGS` because the email section below them already sends the same three things. Attachment MIME type is derived from the filename (`_attachment_type`) — two transports hardcoded `application/pdf`, and a plan is as often a photo of a drawing.

### Email
- **Inbound: the bot answers email too** (`process_inbound_emails`, 5-min cron), but **EMAIL IS REPLY-ONLY: it answers only people already in the system with a WhatsApp record, and no email ever creates a lead** (2026-08-24 rule; cold-email intake and its `INBOUND_LEAD_ADDRESSES` address->tenant routing were removed). A reply on a thread we started is matched by the `<apt-{id}.…>` Message-ID (or a legacy `[APT-{id}]` subject tag); an email with no thread reference is matched to a lead by `customer_email` (`_known_lead_for_sender`, most recently updated wins, subject folded into the customer's turn since off-thread the subject often IS the request). Either way the matched lead must pass `_is_whatsapp_lead` — a real phone number, not a synthetic `email_…` (legacy cold-email row) or `quotation_only_…` key — so the check is about the LEAD, not about how the mail matched. Everything else (receipts, support tickets, strangers writing in cold) belongs to nobody in the CRM and is left UNREAD for a human. No routing is needed for multi-tenancy: the matched lead carries its own tenant. **Two gates sit in front of the rule** (the polled inbox is the operator's personal Gmail, so the bot once opened leads on Stripe receipts and replied to them): (1) `_is_our_own_mail` drops our own traffic BEFORE the thread tag is trusted — the polled address, `DEFAULT_FROM_EMAIL`, every tenant `customer_from_email`/`email_sender`, `PLATFORM_NOTIFICATION_EMAIL`, `PLUMBER_NOTIFICATION_EMAILS`, the owner accounts, and anything on `PLATFORM_EMAIL_DOMAIN`; the Bcc copy of our own customer email carries the same `[APT-{id}]` reference the customer's reply does, so an APT match alone is not proof a customer wrote. (2) `_is_automated` drops machine mail (Auto-Submitted / List-Id / X-Autoreply headers, no-reply & mailer-daemon & receipt/billing/stripe addresses, bounce/out-of-office/receipt subjects) — without that guard the bot email-loops. Mail the bot declines is left **UNREAD** and its body is never downloaded: fetches use `BODY.PEEK` (`_fetch_unseen_headers` → gates → `_fetch_message`), because a plain `RFC822` fetch silently marks the operator's own mail read. Any new mailbox-touching code must keep the peek-then-gate order. A `--dry-run` neither replies nor marks anything seen.
- Email-only leads have no phone number, so they are excluded from proactive WhatsApp: `send_followups` skips `email_`/`quotation_only_` prefixes and `send_reminders._send_wa` refuses any non-numeric recipient. Any new synthetic-key lead type must do the same.
- **Two sending identities per tenant** (`bot/plumber_notifications.py`): `tenant_platform_from_email` → `<tenant-slug>@notifications.homexmedia.com` (`PLATFORM_EMAIL_DOMAIN`) is used for **internal** alerts — the mail to the operator and to the tenant's own inbox; `tenant_customer_from_email` → the tenant's own domain address (`TenantProfile.customer_from_email`, set on the Profile page) is used for **everything the tenant's clients receive**, falling back to that platform sender when unset, and to `DEFAULT_FROM_EMAIL` only for tenant-less platform mail (password resets). Resolution happens once at the `send_email_to_recipients` choke point and is threaded to all three transports as `from_email`/`reply_to`; only `send_plumber_notification_email` passes an explicit `from_email`. DNS: `notifications.homexmedia.com`, and any tenant domain, must be SPF/DKIM-authenticated in Brevo before it delivers.** Note `email_sender` is a recipient inbox, `customer_from_email` a sending identity — never conflate them.

### Quote templates: client vs global
- **The BUILDER is one template, `bot/pages/quotation_template_form.html`, for create AND edit, and it is the QUOTE EDITOR's layout** — same cards in the same order, the same `.pbq-items-panel` where what is already added stays on screen, the same `.pbq-totals` (its two default-cost inputs carry `pbq-total-input`, the same compact figure box the quote's labour and transport use), and the same `.pbq-actionbar` closing the page on Save. `OneTemplateBuilderTests.QUOTE_SKELETON` measures that parity rather than asserting it: the same blocks, in the same order, on both screens. Building a template is building a quote; a builder that looked like a different product taught a second set of habits for the same job. `create_quotation_template.html` / `edit_quotation_template.html` (835 + 972 lines) are DELETED and a test asserts they stay gone: they had drifted exactly as the three quote editors had — the edit screen printed every figure in RAND ("R 0.00") on a business quoting in US dollars, put Add Item in a card header instead of under the list, and carried a warning block create had never heard of. `TEMPLATE_FORM_TEMPLATE` is the single name and `template_form_context()` the single context builder (`template_mode` = new/edit, `quote_currency` from the lead's own `TenantConfig.currency` — never a symbol typed into the markup).
- The items are still a Django FORMSET (`items-0-description`, …), not the quote editor's JS array; only the markup around those inputs changed, from a nine-column table to one `.pbq-item` card per form. Removing a card ticks the formset's own DELETE box — the row must reach the server marked for deletion, not merely vanish from the DOM — and blank scaffolding cards are dropped the same way on submit, since the formset validates `unit_price` and an untouched spare would fail the save. `extra` dropped 5 → 0 (`min_num=1` renders the one blank card): the quote editor opens on ONE blank item and adds the next when that is filled, and five blanks were cheap as table rows but five screens of scaffolding as cards. **The item card is the quote's card** — description, then qty and unit price side by side, then the line total; `category` and `is_optional` are real fields (the detail page shows them, Duplicate carries them) so they sit in a `<details>` that is SHUT on load rather than being deleted, and a cloned card resets it. What cannot match is what a template does not have: no client or project cards, no lead picker, no document preview, and an action bar of Cancel / Add Item / Save because there is nothing to email, WhatsApp or download.
- **The operator's "share with every client" checkbox is on the EDIT screen too**, and re-checked server-side there as it already was on create. It was create-only, so a template shared by mistake could never be taken back.
- `QuotationTemplate.is_global` (migration 0078). A CLIENT template belongs to its tenant; a GLOBAL one is written by the operator and offered to every tenant read-only, with **Duplicate as the way to make it yours** (`duplicate(new_name, tenant, created_by)` drops an editable copy in the caller's workspace, never another global).
- **`QuotationTemplate.for_user(tenant, user)` and `.editable_by(user, tenant)` are THE single readers** for visibility and permission. A plain `.filter(tenant=…)` hides the global set; a plain `.all()` leaks one tenant's templates. **Visibility is not permission** — a client can SEE a global template and must not edit it, so the two questions are asked separately (`EditQuotationTemplateView.get_object` re-asks after `get_queryset`).
- **SECURITY, fixed:** `duplicate_template`, `delete_template` and `toggle_template_status` fetched by bare pk with no scoping at all, so **any staff user could delete another tenant's template** by guessing a pk. All three now go through `_editable_template`.
- `is_global` on the create form is operator-only AND re-checked server-side in `form_valid` — hiding a checkbox is presentation, not permission. The list's counts are taken over the same set the rows come from (counting by tenant alone excluded every global, so the totals disagreed with the list).

### Quote templates: the builder is the tenant's OWN sheet
- **The builder follows the tenant's quote layout, exactly as the quote editors do.** `builder_template_names(request)` reads the same `is_sectioned` switch `get_template_names()` uses on every quote screen, so a sectioned tenant builds their templates on their own document (`bot/pages/quotation_template_sectioned_form.html`) and a flat tenant keeps `quotation_template_form.html`. Tenant data, never a slug check. Building a template is building a quote, so the builder that looked like a different product taught a second set of habits for the same job — that rule was already why create and edit are one file; this extends it to WHICH sheet.
- The sectioned builder IS the paper quote: the tenant's letterhead (`quote_letterhead.html`), numbered sections each with their own SUB-TOTAL, **QTY | DESCRIPTION | UNIT PRICE | TOTAL PRICE** in the sheet's own order as ONE table, MATERIALS SUB-TOTAL / ADD: Labour / Transport / SUB-TOTAL / VAT / GRAND TOTAL, and the banking + signature foot (`quote_footer.html`). What differs is only what a template does not have: **no client** (the `.bq-meta` grid holds the template's own name, job type and notes in the same shape), **no per-job figures** (VAT, deposit and terms are the business's own Profile defaults, shown where the quote will carry them and greyed — a discount is per job and the paper document has no such row), and **no send** (Cancel / Add Section / Save). Pinned by `SectionedTemplateBuilderTests.SHEET_SKELETON`, which measures the blocks in order rather than asserting the look.
- **Sections are `QuotationTemplateItem.section` + `quantity_text`** (migration 0087), mirroring the same two fields on `QuotationItem`, with `Meta.ordering = ['sort_order', 'id']` — consecutive rows sharing a heading are one section, so the order the lines were typed in IS the grouping. `group_formset_by_section(formset)` groups the FORMS by their **bound** section value, so a rejected save hands back the headings the plumber typed rather than the ones the row was last stored under.
- **It is still the same Django FORMSET** (`items-0-description` …), only the markup around those inputs is the sheet's. The heading is typed once and written onto each row's hidden `section` on input; `quantity_text` is the visible QTY cell and the numeric `quantity` is derived from it (`19 length` → 19); a row added in the browser is stamped out of `{{ formset.empty_form }}` with `__prefix__` replaced, so it posts exactly the fields a server-rendered row does; `sort_order` is re-stamped in DOM order on submit, or a row added to section 1 after section 2 exists would sort into section 2.
- **The flat builder carries `section` and `quantity_text` hidden even though it shows neither** — a global template built on the sectioned sheet can be opened there by the operator, and a field the form did not render comes back blank and wipes the grouping. Editing the NUMBER on that screen clears the wording it no longer matches; editing the price leaves it alone.
- **A template arrives on a quote as its OWN sections.** `useTemplate` in the sectioned editor groups the API's items by heading and calls `addSection` per group; a template with no sections is still one block named after the template, which is what every template used to do. Two long-standing bugs fixed on the way: `?template_id=` was never implemented in `quotation_templates_api`, so the whole list came back and both editors read `[0]` — **the most-used template named the section and supplied the default costs, whichever row was actually tapped** — and the payload never carried `default_labor_cost` / `default_transport_cost` under the names the editors read, so a template's default labour silently arrived as 0 on every quote. `template_items_api` also fetched by **bare pk with no scoping**, handing any staff user another tenant's item list and prices; it goes through `_visible_templates` now, like every other per-template action.
- Known, untouched: the template DETAIL page's "Use Template" button posts to `use_template` with no appointment, and `Quotation.appointment` is non-null, so that button 500s (the working route is `use_template_for_appointment`). The detail page also lists items flat, without their sections.

It is the `/quotations/new/` layout, made the layout everywhere. - Wide tables never scroll sideways: read-only ones take `.pbq-table--stack` and editable ones `.pbq-table--edit`, and **every `<td>` must carry a `data-label`** — below 768px the header row is hidden and each cell prints its own label as the row becomes a card. `.pbq-table--edit` uses `!important` on `display`/`width` deliberately: it sits over legacy page CSS that pins column widths with `nth-child`, which would otherwise outrank it. It used to be `position: sticky` offset by `--bottom-nav-h`, which sat over the form on a short screen and made every quote screen read as a floating toolbar; the `.pbq-page--barred` modifier existed only to clear it and is retired with it, as is the sectioned sheet's own `.bq-actions--bottom` stickiness. **Nothing in the quote layer pins to the viewport** — if a future bar needs to, note that `.pb-content__inner` runs `pb-fadein` with `animation-fill-mode: both`, and a retained `transform` would make it the containing block for fixed descendants (which is why that keyframe ends on `transform: none`; **don't put a `translateY(0)` back**).
- `quotations_list` is `paginate_by = 25` and now renders page controls; without them everything past the first 25 quotes was unreachable.

Past `ITEMS_CAP_AT` rows JS adds `.is-capped`, which gives the list its own scrollbar — Add Item is deliberately **not** viewport-sticky, since a second sticky element lands behind `.pbq-actionbar` on a phone. Revealing a new row uses `block: 'nearest'` (or a scroll of the list's own box to its bottom); `block: 'center'` pushed every item already added out of the viewport, which with the keyboard up left the blank new row as the only thing on screen. `renderItems` restores `scrollTop` across its innerHTML rebuild.
- The template builders' totals were moved **out of the table's `<tfoot>`** into a `.pbq-totals` block below the list — inside the table they would scroll away with the rows once the list is capped. Their `addNewRow(reveal)` only scrolls/focuses when `reveal` is true: `checkIfNewRowNeeded` auto-appends a row as you type a price, and focusing there would yank the caret out of the field being filled.
- **Watch the temporal dead zone in these handlers.** `create_quotation_template` calls `calculateAllTotals()` at the top of its `DOMContentLoaded`, and that reads `ITEMS_CAP_AT`; declaring the `const` further down threw a `ReferenceError` that killed the whole handler — no totals, no delete buttons, no auto-add — on a page still returning 200. Static checks can't see this; run the rendered page in jsdom.
- **Line-item ids come from a monotonic `nextItemId()`, never `Date.now()`.** Every lookup is by id, and two items added inside the same millisecond shared one — editing one edited both, removing one removed both.

### The editor's own workflow: find the lead, start from a template, save, send
- **The screen is ordered the way the job is done**, on BOTH layouts: who the quote is for and where its lines come from at the TOP, the sheet in the middle, and everything that DOES something in one bar at the BOTTOM. The sectioned sheet had Save alone above a sheet nobody had filled in yet, no template loader, no lead picker and NO send buttons at all — the plumber saved, navigated to the quote page, and sent from a screen they had already left.
- **`bot/includes/quote_lead_picker.html` is the one lead picker**, on both editors and only where a lead can still be attached (never on an edit, which already has one). It renders the search box and calls `window.quoteLeadPicked(lead)`; each editor defines that and fills its own fields, so the include knows how to FIND a lead and never what a sheet does with one. `appointment_search_api` had existed for exactly this and no screen used it: the only route to a quote for a lead was to find them in the inbox and open them first. **An EMPTY query now answers with the 8 most recent leads** — "who have I been talking to?" is the real question, and returning nothing until two characters were typed made attaching a lead a memory test. It also matches on email, and never offers `quotation_only_` / `email_` stubs.
- **Three includes are shared by both layouts** rather than copied into each: `quote_template_modal.html`, `quote_email_choice_modal.html` and the picker. Their CSS lives in `quote_responsive_css.html` (the `.pbq-choice*` rules moved there from the flat page): **a `<style>` block rendered AFTER the document moves the "past the stylesheets" line every parity test measures from**, so shared chrome keeps its styles in the shared layer, never in the include.
- **Every send saves first, on both layouts** (`persist()` → send). Save and the two channels are independent and never disabled; the channels stay separate as they are everywhere else.
- **Save, Email and WhatsApp all hand the plumber back to the page the editor was opened from** (`quote_return_url` → the editors' `RETURN_URL` / `returnToCaller`). Raising a quote is a detour out of a lead's screen, the quotes list or the diary, and the three buttons that finish the job used to end in three different places: a brand-new Save landed on the quote's own view page, an edit's Save left the plumber standing on the editor with only a toast, and a send left them on the sheet with no way of telling whether it had gone. The target is resolved SERVER-SIDE from the Referer at render time, so the plan tab and the lead picker cannot move it, and only the PATH is emitted so it can never be an open redirect; a Referer pointing at an editor (a reload, a hop between the two sheets) is rejected and falls back to the lead's own page, then to the quotes list for a standalone quote whose lead is a synthetic stub. **Two things must not be navigated over:** a WhatsApp handoff whose popup was BLOCKED is running in this tab (return only when `opened` exists), and the manual `mailto:` route is pulling the PDF down through a hidden iframe on this page (hence the longer delay, and `markSent` is awaited now that the page leaves). A FAILED send keeps them on the sheet, which is what needs fixing. Pinned by `QuoteReturnToCallerTests`.
- **A quote is sendable on at least one channel, always.** `Quotation.client_phone` (migration 0086) keeps the number typed on the sheet, because a standalone quote's lead is a stub whose `phone_number` is a synthetic key — that key is what keeps these rows out of every proactive send, so it must NOT be replaced with a real number. `quote_send_digits(quotation, appointment)` is the single resolver (lead's own number, else the typed one, digits only) and both the handoff and `flat_form_context` read it. A missing EMAIL is a missing detail, not a closed door: the quotes list, both client copies and both editors point at the screen where the address is added instead of showing a disabled button, and WhatsApp is never gated behind it.
- **The deposit is a figure on the quote, adjustable per job** (`Quotation.deposit_percent`, migration 0086). It only ever existed as words in the payment terms ("deposit 75%"), which could be printed but never changed for a job agreed differently. Asked for as a PERCENTAGE with `Quotation.deposit_amount()` derived from the grand total — a stored amount would stop agreeing with a total that moves on every edit. It starts from the tenant's own `letterhead['default_deposit_percent']` (Profile page), is clamped 0-100 in the editor AND in `_deposit_percent()` on the way in, and **0% means the row is absent from every document** — screen, client copy and PDF, both layouts. Absent from a payload means UNCHANGED on an edit, so a caller that never heard of deposits cannot clear one.
- Two long-standing breakages fixed on the way: `create_standalone_quotation_api` did `from .models import …` inside `bot/views/`, so **every save of a quote with no lead 500'd** — the "New Quote" screen could not save at all; and `_sectioned_form_context` took only the quotation, so the sectioned EDIT screen rendered CLIENT / CONTACT / ADDRESS / EMAIL empty and then refused the save ("enter the client name" about a name it had forgotten to draw). The standalone endpoint now also stores sections, trade quantities, discount, VAT, deposit and terms, so a sectioned quote raised without a lead reopens as the sheet it was; `duplicate_quotation` carries the same set.
- **The quote screen has two tabs stuck to the top: QUOTE and PLAN** (`bot/includes/quote_plan_tabs.html`, one include for both layouts). A quote is typed off a drawing, and the drawing was on the LEAD's page: the loop was leave the quote, find the plan block, open the plan, read one number, come back, find your place in the item list, twenty times a quote, on a phone, on site. **Switching tabs does not navigate** — the quote panel (`#pbqQuotePanel`, which is the whole existing sheet, wrapped) is HIDDEN, never unloaded, so every field, the item list, its own scrollbar and the CARET come back exactly as they were; `show()` saves and restores `.pb-content`'s `scrollTop` (the page itself never scrolls — the shell is `height:100vh; overflow:hidden`, so `window.scrollY` is always 0 here) plus `#itemsScroll` and the focused field's selection range, and blurs on the way out so the plan gets the whole screen. The draft autosave is the safety net under this, not the mechanism. Behind the second tab: the customer's **own words verbatim** (`project_description`, `white-space: pre-wrap` — they typed it as a WhatsApp message and the line breaks are part of what they said) then every file they sent. **`quote_lead_panel(lead)` is the one resolver**, called by BOTH `flat_form_context` and `_sectioned_form_context`, and files are addressed by INDEX into `get_all_uploaded_files()` and streamed through `serve_document` — never a storage URL, since R2's presigned links expire and a mis-set backend hands back a bare path that 404s (same reason the lead page links them that way). **Media loads on FIRST OPEN** (`data-pbq-src` -> `src`), because a plan is often several MB and this screen is used on mobile data. A lead with neither words nor files gets NO tab bar: a tab that opens on an empty page is a dead control. The full-screen link is `target=_blank` on purpose — an iPhone renders only the first page of an embedded PDF, and leaving the page is exactly what the draft covers. The include's script wires on **DOMContentLoaded, not at parse time**: it sits ABOVE the panel it switches to, and looking `#pbqQuotePanel` up inline left both tabs inert. Printing from the plan tab still prints the quote (`beforeprint` switches back, and the print stylesheet un-hides `#pbqQuotePanel[hidden]`). **This bar is the ONE deliberate exception to "nothing in the quote layer pins to the viewport"** (owner rule, 2026-09-08): that rule was written about a permanent ACTION bar sitting over a form nobody had filled in yet, while this is the only way back from the plan and has to be reachable from wherever the plumber has scrolled. Pinned by `QuotePlanTabTests`.
- **A quote in progress survives Back, a closed tab and a dead battery.** Both editors keep the sheet in `localStorage` as it is typed (debounced 400ms) and flush it on `pagehide` / `visibilitychange:hidden` / `beforeunload` — the events that survive a tab close or a phone switching apps, where `unload` does not — so the keystroke still sitting in the debounce is not the one that is lost. On the next visit to that editor the saved record loads FIRST and the draft is laid on top, because the draft is the more recent thing the plumber typed. **The key follows the QUOTE, not the screen** (`draftKey()` / `bqDraftKey()`): once a save returns a row id the draft belongs to that row, so the same work is found again from the edit screen AND a fresh create screen for the same lead opens blank rather than restoring a quote already raised. A save clears every key the page could hold one under (`draftKeysSeen`), not just the one this page load wrote — the copy that reopens the screen is whichever is still on disk, and the key it was written under may belong to a PREVIOUS page load (that is the bug the jsdom run caught: `new_new` survived the save and came back on the next new quote). Only the sheet's own inputs mark it dirty (`isDraftField` / `bqIsDraftField`): the lead picker's search box and the template modal's live on these pages too, and a draft written from them greets the next visit with "restored your unsaved changes" over a sheet nobody touched. Best effort throughout — every storage call is wrapped, so a browser with site data blocked simply behaves as before. **The quote TEMPLATE builder has none of this**: it is a Django formset, not the editors' JS array.
- Pinned by `QuotePlanTabTests`, `QuoteDraftAutosaveTests`, `LeadPickerTests`, `QuoteDepositTests`, `QuoteSendableWithoutEmailTests` and `SectionedEditorWorkflowTests`. The editors' JS is exercised in jsdom against the dumped pages (`bot/test_dump_quote_pages.py`) — static checks cannot see a handler that throws.

### The detail form's date and time
- **`Appointment.active_slot_field()` is the single resolver for WHICH datetime a row's appointment lives in**, and `_reschedule_slot` delegates to it. One row can hold two - `schedule_job_appointment` flips `appointment_type` and fills `job_scheduled_datetime`, leaving the finished site visit in `scheduled_datetime` - so the bot's reschedule flow and the dashboard's own edit form must not answer this question differently.

### The outbound chain, and the one step that skipped it
- **`finalise_outbound(reply, appointment, message_body)` is every rewrite a reply gets between composition and the wire**: the reply check, the memory check, **the unbacked-confirmation stripper**, the fee stripper, the repeat-free-visit stripper, the visit-price note and the dash stripper, in that order. It exists because **STEP 0 (multi-intent compose) sent its own reply straight to `delayed_response` and skipped all of it** — so a fee tenant's multi-intent answer could have promised a free visit with nothing to correct it, and no reply from that path was ever de-dashed. Any new send path calls this rather than repeating the chain.
- **We never tell a customer they have an appointment the row does not have** (`strip_unbacked_confirmation`). Whether a booking EXISTS is the biggest of the things the customer must be able to trust, and it was the only one still improvisable by the model. With the booking flow deadlocked (see `_job_is_known`), barmak lead 1144 got "Thursday 3pm works. We'll confirm the visit." straight from DeepSeek, twice, on a row whose status never left `pending` - nothing in the diary, the plumber never told, and the lead back ten hours later asking whether Thursday was real. The stripper drops any SENTENCE claiming a booking exists or promising to make one official, and is **inert on a confirmed lead**, which is what lets the real confirmation copy through untouched (it only ever sends after `status='confirmed'`). **A promise to confirm is treated exactly like a claim of having confirmed** - "we'll confirm" is what a lead reads as "I'm booked", and nothing was running behind it. **A question is never a claim** ("Shall I lock that in?", "Want me to book you a time?"): every pattern is an assertion, or the close itself would be stripped. When the claim was the WHOLE message it is replaced by the true thing, which is also the close. English only on purpose - the Shona close "Ndokubhukira ... here?" is asking PERMISSION to book, and a pattern loose enough to catch a Shona claim catches that ask instead. Pinned by the `booking claim` cases in TEST 0.
- **The proof step honours `retry_count` like every other scripted ask.** `_get_first_pass_question` IS the `retry_count == 0` script and does not check the count itself, so the show_work branch calling it directly re-sent the availability question word for word 60 seconds after the quote route had asked it (barmak 1144, 07:36 and 07:37). Already asked now means the photos ride out with the deterministic `photo_followup` instead. A TEST 0 case asserts no call site in `whatsapp_webhook.py` reaches that script without reading the count first. `show_examples` also counts the images it is actually sending - "Here are a couple" over a single photo is a small lie a customer notices immediately.
- **DeepSeek READS BACK every reply before it is sent** (`bot/response_check.py`, `verify_and_refine`, ON by default via `PLUMBOT_REPLY_CHECK`). It runs FIRST in the chain, on the composed draft, because everything else in the chain is a rule and a rule cannot catch the fault this exists for: a reply that breaks no rule and is still obviously wrong to anyone who read the conversation ("tomorrow or this Tuesday?" to a lead who just said they are out of the country until December - barmak 1005). It is a READER, not a guard: it may only CORRECT, never block, and it is fenced AGAINST the model - no new figure, no new promise word (free / discount / guarantee / mahara), no language change, no growth past 1.6x. A refinement that breaks a fence is REJECTED and logged and the draft still sends, and every failure mode (timeout, bad JSON, refusal) **fails open**. Whatever it returns then goes back through the same deterministic strippers, because a refinement is just another draft and gets no exemption - `ChainOrderTests` pins that ordering. `check=False` skips the READER only, for copy with nothing contextual to get wrong (a fixed template); never pass it for anything the flow composed.
- **A path that writes to the wire itself must call `_finalised_for_send`.** Most replies reach the customer through `delayed_response`, where the split marker is flattened and every caller has already finalised. **The photo path did neither**: `send_previous_work_photos` sent its lead-in and its follow-up straight to `send_text_message` from its own thread, skipping the ENTIRE chain. The follow-up is the one that bit - it carries the scripted next question, which for `availability_date` IS the availability ask, the exact message `ensure_visit_price_note` exists to attach the call-out fee to - so a fee tenant whose ask rode out behind the photos named no fee and the lead met the figure later, which is the nasty surprise the once-only fee rule was written to prevent. The same gap could promise a free visit for a tenant that charges with nothing downstream to take it back. `_finalised_for_send` runs the chain, flattens the marker, returns '' when the chain decides there is nothing left to say (the caller then sends nothing rather than a draft the chain rejected), and fails open on an unexpected error. The lead-in takes `check=False`, the follow-up the whole chain. `message_body` is threaded through `send_previous_work_photos` so the strippers can still tell an explicit "what does the visit cost?" from an unprompted repeat. Pinned by `PhotoPathGetsTheChainTests`. **Still outside the chain, deliberately:** plumber alerts (not customer copy), the booking confirmation (`send_confirmation_message`, deterministic copy the model must not rewrite) and every cron message - `send_followups` / `send_reminders` get the deterministic strippers via `dequalify_free_visit`, and the post-visit / plan-quote / visit-proposal emails are fixed templates with no model output to read.
- **STEP 0 recorded the priced intents it sent but never checked them.** The single-intent branch has always called `_has_sent_pricing_for_intent`; this one only called `_mark_pricing_intent_sent`. A lead who repeated themselves got the identical price block again (prod, Barmak lead 974, 2026-09-03 13:17 and 13:24, both logged 🧩 Multi-intent compose). It now drops through to the normal flow when every intent it would answer is a price already sent, while a genuinely new question in the mix is still answered.
- **`compose_multi_answer` is English-only** — every snippet, the combined-pricing line and the closer. A Shona lead got an English wall of prices where the single-intent path answers in Shona, so a Shona message now returns None and goes to that path: one answer in their own language beats two in the wrong one. **The scripted first-pass question bank (`_get_first_pass_question`, 13 branches) is English-only too and is NOT yet fixed** — that is why a Shona lead is asked "What area are you in?" in English.

### Conventions to follow
- Reuse existing infra; no new dependencies without being asked. Preserve WAMID dedup and exit-signal-first ordering.
- **Keep the quote out of the rule engine** — thread it as `quoted_context` to classification/LLM calls only; any new outbound send path must stamp its WAMID (`attach_message_id` / `record_sent_media`) or quotes to it break silently.
- **No Homebase value may reach another tenant's customer.** Every figure, number, name and place in customer-facing copy or an LLM prompt resolves through the lead's own tenant: prices via `TenantConfig` (`catalogue_price_lines`, `price_components`, `freestanding_tub`, `cheapest_labour_rate`), the plumber's line via `Appointment.plumber_contact()` (webhook alerts go through `_plumber_wa_number`; `send_reminders` groups briefings per tenant via `_tenant_plumber` and gives customers `_lead_plumber_contact`), the name via `business_name_for()` / `plumber_display_name()`, the place via `location_short()` / `location_city`. **Absent means omit, never borrow** — a tenant with no tub price gets the free-visit deflection, one with no plumber number gets the email alert only. The `PLUMBER_PHONE_NUMBER` / `PLUMBER_NAME` env vars are homebase's legacy fallback and must not be used for a lead that has a tenant. Fixed 2026-08-21: catalogue price sheet, tub pricing, both plumber-alert paths, the unified + service-type classifier prompts, and the "based in Harare" / "as little as US$20" / "the plumber's name is Takudzwa" copy were all still hardcoded.
- **Hours are the tenant's own week, plus an optional 24/7 emergency tick.** `business_hours['emergency_24h']` (a key on the same JSON — no column) is set from the Profile editor and the intake wizard; `TenantConfig.emergency_24h()` / `emergency_sentence()` / `emergency_tag()` are the only readers, and every hours-copy site (`_working_hours_line`, `_hours_clause`, `_open_hours_clause`, `_quick_hours`, `_grounding_facts`, `_hours_clock`, `_emergency_fact`, the hours FAQ fact, the email prompt) goes through them. Out-of-hours refusals end with the emergency offer instead of dead-ending the lead (`_emergency_offer` in both `models.Appointment` and `availability_mixin`). It does NOT widen the booking window — regular slots stay inside the tenant's day. Absent means omit: never promise 24/7 for a tenant without the tick.
- Prefer deterministic resolvers over LLM round-trips for short/fuzzy strings (see the quote intent fix); reserve the LLM for genuinely ambiguous language.
- **The free visit is said ONCE, at the start.** "free site visit" / "free assessment" / "free of charge" was asserted in ~77 copy sites and landed in almost every reply, follow-up and reminder; said once it is the USP that earns the appointment, said six times it reads as pleading and drags a lead who has already accepted the visit back onto cost. `strip_repeat_free_visit(reply, appointment, message)` de-qualifies it at the SAME outbound choke point as `strip_free_visit_claims` (so it catches the LLM paths, not just the hardcoded copy): the first reply that pitches the visit goes out untouched, every later one loses the claim. **The pitch survives — only the price claim comes off**, so "a free on-site visit" becomes "an on-site visit" (article fixed) rather than the sentence being dropped, which is the opposite of the fee stripper's rule and deliberately so: there a false promise is the worst outcome, here a deleted pitch is. Shapes handled: adjective, leading clause ("The visit is free — our plumber will…" → the rest is promoted), trailing clause, adverbial ("free on/when/at…"), a label parenthetical ("(Free site visit)"), Shona `mahara`, and a guard that never leaves a sentence hanging on its verb. `asks_visit_cost` is the override — a lead who asks what the visit costs gets the straight answer however often they ask (customer's own words beat the gate), and it reads the FAQ's own `free_quote` triggers via `faq.visit_cost_triggers()` so the two can't drift. `_visit_fact_line` drops "is free" from the LLM grounding fact once it's been said, so the model isn't fighting the stripper. The cron commands call the same resolver through `dequalify_free_visit(lead, message)` — applied where the message is composed, so `--dry-run` previews what actually goes out. `freestanding` / `free-standing` is guarded everywhere: it is not a price claim.
- **A tenant who CHARGES for the visit follows the same once-only rule.** `strip_free_visit_claims` used to append `visit_cost_sentence()` to every reply that mentioned the visit at all, so a fee tenant's lead read "The call-out to quote is US$20." on all five turns, including after they had booked — the same complaint as the repeated "free", with a harder number.
